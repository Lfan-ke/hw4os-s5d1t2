# 03b · 动态链接加载器 思考题（参考答案）

> 判据：答案非空且命中关键字（如 `共享` / `一份` / `GOT` / `私有` / `符号解析` /
> `基址` / `重定位` / `首次调用`）即过 `ESSAY_PASS`。

## 1. 静态 vs 动态：空间与「修 bug」的代价

**静态**把整份 libc 拷进每个可执行（`static_total_space = n*(own+lib)`）：n 个程序就有 **n 份**
相同代码，空间随 n 线性膨胀；libc 出了 bug，每个程序里都嵌着旧代码，必须**逐个重新编译/链接**
才能修好。**动态**只把库留**一份共享**（`dyn_total_space = lib + n*(own+小GOT)`），程序里只存
名字引用 + 一张小 GOT；修 bug 只要**换那一份 `.so`**（或打补丁），所有引用它的程序**一起生效**，
无需重编。空间省在「库不再各塞一份、只算一份 + 各自一张小 GOT」。

## 2. 为什么 GOT 每进程私有，而库的代码可以多进程共享？

库的**代码段是位置无关码（PIC）+ 只读** → 物理内存里只存一份，多个进程的页表把**同一物理页**
映射进各自地址空间（内核按 inode 的 page cache 自动共享），永不写、永远共享。但每个进程把库
加载到的**基址不同**（ASLR 随机化），同一个 `puts` 的**真实地址因进程而异**；这些「会变的地址」
集中放在**可写的 GOT**（数据段）。`ld.so` 把解析出的地址写进**本进程私有的 GOT 页**（写时触发 COW
私有化）。所以：**只读代码共享一份、可写 GOT 每进程一份**——PIC 用 GOT 间接正是为了不改代码页、保住共享。

## 3. lazy 绑定 vs now 绑定的取舍

`lazy`：符号在**首次调用**时才解析回填（本实验只调 `puts` 时只解析 1 个），**启动快**、未用到的符号
不花解析开销；代价是首次调用有一次解析延迟，且 GOT 运行期可写（易被「GOT 覆写」攻击）。
`now`：加载时**一次性解析全部**（本实验解析 3 个），启动稍慢、可能解析了用不到的符号；好处是之后
运行平稳、且可把 GOT 段**标只读（RELRO）**。现代发行版默认 `BIND_NOW + RELRO` 是**安全优先**：
全部解析完就锁死 GOT，杜绝运行期改 GOT 的攻击，代价是略慢的启动。

## 4. 我们的模型离真实 `ld.so` 还差什么？

本实验 `lookup` 按【符号名 key】在共享库里查地址，对应真实 `ld.so` 的**符号解析 `find_sym`**
（遍历依赖图按名字找定义，真实地址 = **库基址 + 库内偏移**，正是 `dyn_total_space` 里那个 `base+off`）。
模型简化掉的真实机制（举例）：① **重定位类型**——真实 GOT 回填要按 `R_X86_64_JUMP_SLOT` /
`R_RISCV_JUMP_SLOT` 等**重定位项**逐条处理，还有 `RELATIVE`/`GLOB_DAT` 等；② **ASLR 随机基址**——
真实库基址每次运行随机，故各进程 GOT 值不同；③ **page cache 按 inode 共享**——真实"一份共享"是内核
缺页时按 `(inode, offset)` 复用物理页白送的，`ld.so` 全程不知道别的进程。补齐这些，就成了正经实验
`S09b-linking` 里用真 `gcc -c`/`-shared -fPIC`/`readelf -r`/`ldd` 跑出来的版本。
