# 19-isa-emulator 思考题参考答案（essay 变体）

## 1. 用一句话概括 CPU 的本质，并解释「取指→译码→执行」三步各做什么。

CPU 的本质就是一个**永不停歇的「取指→译码→执行」循环**（fetch-decode-execute loop），
靠 `pc` 这根指针一条一条地往前走。

- **取指 fetch**：以 `pc` 为地址，从内存里读出一条机器码（RV32/RV64 定长指令是 4 字节）。
  这一步只关心「字节」，还不知道它是什么指令。
- **译码 decode**：把这 32-bit 按 ISA 编码规则拆开——`opcode`/`funct3`/`funct7` 决定
  这是哪条指令、属于哪种格式（R/I/S/B/U/J），再抽出 `rd`/`rs1`/`rs2` 和**立即数**
  （并按格式做**符号扩展**）。译码的产物是「这条指令到底要干什么」。
- **执行 execute**：按译码结果动手——做 ALU 运算、读/写内存、更新某个寄存器、
  或改写 `pc`（分支/跳转）。执行完 `pc` 指向下一条，循环重新开始。

模拟器（NEMU/QEMU/Spike）不过是用一段**软件**忠实地跑这个循环：`regs[32]` 是寄存器堆，
一块字节数组是内存，`pc` 是程序计数器，`step()` 跑一次三步。真硬件则是把这三步铺成
组合逻辑 + 时序逻辑，在时钟驱动下并行/流水地完成同一件事。

## 2. 为什么说 ISA 是「软硬件之间的契约」？指令编码里的字段（opcode/funct/imm）体现了什么？

ISA（指令集架构）是**软件和硬件谁都不能单方面违约的接口规范**：

- 对**软件/编译器**：它承诺「只要我发出符合 ISA 的指令序列，任何实现了该 ISA 的硬件
  都会按规定语义执行」。于是同一个 RISC-V 程序能在 NEMU、QEMU、Spike、以及各家真芯片上
  跑出一样的结果——软件不必关心硬件是单周期、流水线还是乱序超标量。
- 对**硬件**：它只需保证「实现 ISA 规定的可见行为（寄存器/内存/异常的最终效果）」，
  内部怎么实现（缓存、分支预测、重排）是自由的。

指令编码就是这份契约的**二进制条文**：`opcode` 划出指令大类与格式，`funct3`/`funct7`
进一步细分具体操作（如同为 `OP` 的 `add` vs `sub` 仅差一个 `funct7` 位），
`rd`/`rs1`/`rs2` 用固定位段指明操作数寄存器，`imm` 用规定的拼接/符号扩展方式编码常数。
RISC-V 还特意把寄存器号、立即数高位放在**跨格式固定的位置**，让硬件译码器更省事——
这正是「契约」为实现友好而精心设计的体现。本课里 `decode()` 把这些字段一拆，
软件和硬件就站在了同一份契约之上。

## 3. DiffTest（差分对拍）为什么强？它把「最终错了」变成了「从哪条指令开始错」。

DiffTest 的威力来自两点：

1. **可信 oracle（黄金参考）**：用一个**独立的、被广泛验证过的**参考实现
   （NEMU 里是 QEMU/Spike，本课里是预先算好的黄金轨迹）当裁判。两套实现独立写出，
   同时出一模一样 bug 的概率极低，于是「参考」几乎可以当成「正确答案」。
2. **抓第一处分歧**：不是等程序跑完才比对最终结果，而是**每执行一条指令就比对一次**
   寄存器/PC 快照。一旦发现不一致立即停下——这第一处分歧，**就是第一条出错的指令**。

这把调试从「最终结果错了，但错在几万条指令里的哪一条？」这种大海捞针，直接缩小成
「第 k 条指令的 regX：ref=.. dut=..」一行定位。bug 还没来得及污染后续状态、还没被
覆盖掉，就被当场抓获。NEMU 正是靠它，在实现新指令时第一时间发现「我这条 `sub` 的
符号、这条 `beq` 的偏移、这次 `jalr` 的 `&~1`」错在哪。对照本课：如果你把 `add` 写成
`sub`，DiffTest 会在第一次 `add x5,x5,x6` 处就报 `x5: ref=1 dut=...`，而不会让你
对着最后那个错误的 55 抓瞎。

## 4. 解释器 vs 二进制翻译 vs 真硬件 vs 跨架构模拟器，四者关系？

它们都在「执行指令」，差别在**怎么执行、执行谁的指令、在什么之上**：

- **解释器（interpreter）**：就是本课这种 fetch-decode-execute 循环，**每条指令每次都现场
  译码再执行**。实现最简单、最易做 DiffTest/调试，但每条指令的译码开销重复付出，**慢**。
  NEMU 的基础模式、教学模拟器都是这一路。
- **二进制翻译（binary translation / JIT，对照 `proper/S18-tcg`）**：把一段**客户机指令**
  翻译成一段**宿主机原生指令**（或中间表示再编译），翻译一次、缓存复用，热代码近乎原生
  速度。QEMU 的 TCG、各种 JIT 都属此类。代价是翻译器复杂、要管理 translation cache、
  自修改代码等边界情况。它和解释器是「同一语义，不同执行策略」：慢但简单 vs 快但复杂。
- **真硬件**：把 ISA 直接做成电路（组合 + 时序逻辑、流水线/乱序）。它不是「软件跑循环」，
  而是物理上并行地完成取指译码执行，速度数量级领先，但不可像软件那样随意暂停、快照、对拍
  （所以才有 DiffTest 把软件模型当作硬件设计的「金标准/对照」）。
- **跨架构模拟器（QEMU）**：在**架构 A 的宿主机**上模拟**架构 B 的客户机**
  （如 x86 上跑 RISC-V/ARM）。它通常用二进制翻译求速度，本质仍是「软件实现另一套 ISA 的
  fetch-decode-execute」，只是宿主和客户 ISA 不同。解释器/翻译都可用于跨架构。

一句话谱系：**解释器**是最朴素的「软件 CPU」；**二进制翻译**是它的加速版；
**跨架构模拟器**是把它（或其加速版）用在「宿主≠客户」的场景；而**真硬件**是同一份 ISA 契约
的物理实现，也是这一切软件模型最终要对齐的对象。

## 5. 引申：这颗玩具 CPU 还能怎么长大？

- **加指令**：补齐 RV64I 的算术/移位/比较（sll/srl/sra/slt/and/or/xor、各 imm 变体）、
  乘除（M 扩展）、更多 load/store 宽度与符号（lb/lh/lw/lbu/...）。每加一条就用 DiffTest 守门。
- **加 CSR 与异常/中断**：实现 `mstatus`/`mepc`/`mcause`/`mtvec`、`ecall`/`ebreak`、
  时钟中断——这样就能跑真正的内核 trap 流程（正是本仓 proper 赛道 S02 在做的事）。
- **接真参考**：把黄金轨迹换成**在线对拍 Spike/QEMU**（NEMU 的 difftest so 模式）：
  每步把 DUT 状态和参考同步、比对，能验证任意程序而不只是预录的小程序。
- **加 watchpoint / itrace**：记录指令轨迹、在某寄存器/内存被写成某值时停下，
  把「第一处分歧」进一步细化到「为什么这条指令会算错」。
- **提速**：从解释器演进到二进制翻译（参照 S18-tcg），缓存译码结果或翻译块。
