# 09b 思考题 · VFS：多文件系统共存于同一组接口（参考答案）

## 1. 为什么需要 VFS

## 答

没有 VFS 时，「支持一种新文件系统」是场灾难：`read/write/open/stat/rename/mmap…` 每个系统调用内部都得写一串
`if fstype==ext4 {…} else if fstype==nfs {…} else if fstype==fat {…}`，加一种 FS 要改**几十处** switch，
而且应用、库、其它子系统全都耦合到具体 FS 的实现细节上。

VFS 的做法就是经典的**面向接口编程 / 多态**：把「随 FS 而变的部分」全部收敛到**一组接口**后面
（Linux 里是 `struct super_operations` / `inode_operations` / `file_operations` 这几张函数指针表；
本课是 `FileSystem` trait / 函数指针表的 `lookup/read/write/readdir`）。
系统调用只对着这层**稳定接口**编程：`sys_read` → `vfs_read` → `file->f_op->read_iter(…)`，
至于背后是 ext4 还是 nfs，VFS 不关心、调用者更不关心。于是新增一种 FS = **实现这组接口、注册进来**，
内核其余代码一行不改。

这和应用层的「面向接口编程」是**同一回事**：一个 `interface Shape{ area() }`，`Circle`/`Square` 各自实现，
调用方只持有 `Shape`。VFS 就是内核版的多态——`FileSystem` 是接口，`ext4`/`nfs`/`devfs` 是实现类，
VFS 是那个「持有接口引用、按需分派」的调用框架。Sun 1986 发明它的直接动机正是接 NFS：
与其把网络文件系统的逻辑塞进每个 syscall，不如让 NFS 实现统一接口、挂进来即可。

## 2. 四大对象

## 答

- **superblock（超级块）**：代表**一个挂载好的文件系统实例**——整盘的元信息（块大小、根 inode、空闲管理、所属 FS 类型与其方法表）。
  一次 `mount` 产生一个 superblock。本课对应**一个 `FileSystem` 实例**（`RamFs` 或 `DevFs`），挂载表里的一项。
- **inode（索引节点）**：代表**一个文件本身**——它的元数据（大小、权限、时间戳）和数据块指针，**不含名字**。
  同一个文件可以有多个名字（硬链接），但只有一个 inode。本课对应**一个节点号**。
- **dentry（目录项）**：代表**「名字 → inode」这条映射**，是路径查找的缓存单元。`/a/b/c` 会沿途生成 `a`、`b`、`c` 三个 dentry。
  名字住在 dentry 里、不在 inode 里——这就是为什么硬链接（多名字一 inode）能成立。本课对应各 FS 的 `lookup(rel) -> node`。
- **file（打开文件）**：代表**一个进程把某文件打开后的句柄**——记录当前读写偏移、打开标志（O_RDONLY…），fd 表里每个 fd 指向一个 file。
  本课对应 `OpenFile{挂载下标, 节点号}`。

**为什么打开同一个文件两次得到两个 file、却共享一个 inode**：因为 file 记的是「**本次打开的会话状态**」——
偏移量、打开模式各自独立（A 进程读到第 100 字节，不该影响 B 进程的偏移）；而 inode 记的是「**文件客观属性**」——
大小、数据、权限只有一份，谁打开都是同一个实体。所以会话级状态（file）按打开次数复制，
实体级状态（inode）全局唯一并被共享。dentry 在中间负责把名字解析到那唯一的 inode。

## 3. mount 与命名空间

## 答

`mount` 把一棵文件系统子树**嫁接**到现有目录树的某个点（挂载点）。挂载后，路径查找逐段下行，
**一旦走到挂载点就「跨」进被挂上来的那个 FS**：`/dev` 是挂载点，于是 `/dev/zero` 的 `/dev` 之后那段 `/zero`
是在 DevFs 内部解析的，与根 FS 无关。这正是本课 `resolve` 做的事：先找路径属于哪个挂载，再把挂载点前缀剥掉、
把剩下的相对路径交给那个 FS 的 `lookup`。

**为什么「最长前缀」是路由关键**：挂载点是嵌套的——`/` 覆盖一切，`/dev` 又覆盖 `/dev/*`。
路径 `/dev/zero` 同时满足「在 `/` 之下」和「在 `/dev` 之下」，但语义上它属于**更深的那个挂载** `/dev`。
若选了更短的 `/`，就会停在根 FS、把整串 `/dev/zero` 当根里的一个名字去找——既找不到、也错过了 DevFs。
所以路由必须取**最长**匹配的挂载点。真实内核不靠字符串前缀比，而是路径查找时逐 dentry 检查「这个目录是不是某挂载的挂载点」，
但效果等价于「最深的挂载赢」。

**和容器 mount namespace 的关系**：一棵全局挂载树是「**一个** mount namespace」。
容器隔离的做法是给每个容器一张**私有的挂载表**（`CLONE_NEWNS`）——A 容器挂的 `/data` 在 B 的命名空间里根本不存在。
本课的 `Vfs.mounts` 就是「一张挂载表」；如果给每个容器各持一个这样的 `Vfs`，让同一条路径在不同表里路由到不同 FS（甚至查不到），
那就是 mount namespace。换句话说：**VFS 的挂载表 + 路由是机制，mount namespace 是「每个容器各发一张表」的策略**——
22-namespace 实验里的 `mount_lookup` 正是本课 `resolve` 的「按容器分表」版本。

## 4. 一切皆文件的延伸

## 答

`/proc`、`/sys`、`/dev` 是**虚拟（伪）文件系统**：procfs / sysfs / devtmpfs。它们挂在目录树上、走同一套 VFS 接口，
所以 `cat /proc/cpuinfo`、`ls /sys`、`cat /dev/zero` 用的都是普通的 `open/read`——这就是「一切皆文件」能成立的机制基础：
**只要实现 VFS 那组接口，你就是一个文件系统**，`cat` 之类的工具完全不知道也不需要知道你背后有没有磁盘。

它们的 `read` 背后**没有磁盘块**，字节是**临时生成**的：

- `/proc/cpuinfo` 被 `read` 时，procfs 的 `read` 回调**现场**去问内核的 CPU 数据结构，把它格式化成一段字符串返回——
  这文件在磁盘上根本不存在，它的「内容」是内核状态的一次快照。
- `/dev/zero` 被 `read` 时，devfs 的 `read` 回调**凭空**用 0 填满调用者的缓冲区返回；`/dev/null` 的 `write` 回调
  直接报告「全收下了」却什么都不存——这正是本课 `DevFs`：`read(/zero)` 返回一串现造的 0、`write(/null)` 返回写了 N 却不存储。

所以本课的 `DevFs` 就是 procfs/devfs 的最小模型：**节点不对应存储，而对应一段「计算」或「副作用」**。
把它和 09-abstract-file 的「文件即 `read/write` 接口」、08-filesystem 的「具体 FS」串起来看：
08 给了「一块真存储的 FS」、09 给了「read/write 这张接口本身」、本课（09b）用 VFS 把它们收进同一棵目录树，
并证明同一张接口下既能挂真存储（RamFs）也能挂凭空生成的虚拟设备（DevFs）——
**「一切皆文件」= 一切都实现 VFS 接口 + 都能挂进同一棵树被同一组工具操作。**
