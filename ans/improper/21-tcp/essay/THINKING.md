# 21-tcp 思考题参考答案（essay 变体）

## 1. 为什么握手是三次而不是两次？

握手的真正目的不是「打个招呼」，而是**让双方都确认对方的「初始序号」已被对方收到**——
连接的本质就是双方对一对序号游标达成一致。要让 A、B 各自的 SYN 都得到确认，最少需要：

1. A→B 的 SYN（A 告诉 B「我从 seq=x 开始」）；
2. B→A 的 SYN+ACK（B 确认收到 A 的 x，并告诉 A「我从 seq=y 开始」）；
3. A→B 的 ACK（A 确认收到 B 的 y）。

第 2 步把「B 的 SYN」和「对 A 的 ACK」合并了，于是三次就够。**两次为什么不行？**
经典反例是「旧连接的延迟 SYN」：A 之前发的一个 SYN 在网络里迷路、滞留了很久，等这条
旧连接早已关闭后才姗姗到达 B。若只要两次握手（B 收到 SYN 就直接建链并开始发数据），
B 就会**为一个早已作废的请求建立一条幽灵连接**，白白占资源、还可能把数据发给一个根本
没在等的 A。三次握手则要求 A 必须再回一个 ACK 来「认领」这条连接——A 看到对一个自己
并未发起的旧 SYN 的 SYN+ACK，会回 RST 而非 ACK，于是幽灵连接建不起来。

一句话：**三次握手 = 双向各一次「我说—你确认」，并用第三次让发起方亲自确认，杜绝
旧的重复 SYN 凭空建连。** 本课里若把客户端的 ACK（TODO ②）省掉，服务器会卡在
`SYN_RCVD` 永远到不了 `ESTABLISHED`——正是第三次握手不可省的体现。

## 2. 为什么主动关闭方要停在 TIME_WAIT 等 2MSL，而不是立刻 CLOSED？

主动关闭方发出最后那个 ACK（确认对方的 FIN）后，进入 `TIME_WAIT`，等 **2MSL**
（MSL = 报文最大生存时间）才真正 `CLOSED`。两个理由：

1. **保证最后的 ACK 能可靠送达**：如果这个 ACK 在网络里丢了，对方（处于 `LAST_ACK`）
   会超时**重传它的 FIN**。若主动方已经立刻 `CLOSED`、把连接状态都丢了，它收到这个
   重传 FIN 就无从应答（只能回 RST，让对方异常关闭）。停在 `TIME_WAIT` 就还留着状态，
   能再补发一次 ACK。等 2MSL 是因为「我的 ACK 一来一回最坏要 2 个 MSL」，等满这段时间
   还没等到对方重传 FIN，才敢确信对方真的收到了。
2. **让本连接的「老报文」在网络中彻底消散**：等 2MSL 能确保这条四元组
   `(srcIP,srcPort,dstIP,dstPort)` 上一切迟到的、游荡的旧包都过期死掉，避免它们
   窜进**下一条复用同一四元组的新连接**里造成串扰。

代价是主动关闭方会在 `TIME_WAIT` 占用端口一段时间（大量短连接的服务器上会堆积，
所以才有 `SO_REUSEADDR` 等手段）。本课用 `tick()` 直接触发 `TIME_WAIT→CLOSED`
模拟「2MSL 定时器到期」，省去真等时间。

## 3. 粗讲滑动窗口与拥塞控制：各自解决什么问题？

两者都在管「一次能往外发多少没被确认的数据」，但针对**不同的瓶颈**：

- **滑动窗口（流量控制，flow control）**：解决「**别把接收方淹了**」。接收方在每个 ACK 里
  捎带一个 `window` 字段，告诉发送方「我的接收缓冲区还能再收这么多」。发送方维护一个
  随 ACK 向前「滑动」的窗口：窗口内的字节可以连发、不必每发一个等一个 ACK（这就是
  为什么 TCP 不是停-等而能跑满带宽）；收到 ACK，窗口左沿右移、把已确认的字节移出，
  右沿按对方通告的 window 扩展。接收方处理不过来就把 window 缩小甚至缩到 0，发送方
  随之放慢/暂停。**对象是接收方的处理能力。**

- **拥塞控制（congestion control）**：解决「**别把中间的网络（路由器队列）压垮**」。
  接收方没满，不代表中间链路不堵。发送方另外维护一个**拥塞窗口 `cwnd`**，靠丢包/RTT
  变化来**猜测网络拥塞程度**：慢启动（`cwnd` 指数增长探带宽）→ 拥塞避免（线性增长）→
  一旦丢包就乘性减小（如 Reno 减半，或超时退回慢启动）。实际能发的量 =
  `min(对方通告窗口, cwnd)`。经典原则叫 **AIMD（加性增、乘性减）**。**对象是网络本身。**

一句话：**滑动窗口看「接收方收得下多少」，拥塞控制看「网络扛得住多少」，真正能发的
取两者的下确界。** 本课为聚焦状态机没实现窗口/拥塞，只做了最朴素的 `seq/ack` 推进。

## 4. TCP vs UDP：各自的取舍？什么场景用谁？

| | TCP | UDP |
| :-- | :-- | :-- |
| 连接 | 面向连接（握手/挥手） | 无连接，一包就走 |
| 可靠 | 确认+重传，保证不丢 | 不保证，丢了不管 |
| 顺序 | 按 seq 重组，保证有序 | 可能乱序 |
| 流控/拥塞 | 有（窗口/cwnd） | 无 |
| 开销/时延 | 头大、有建链 RTT、队头阻塞 | 头小、零建链、低时延 |
| 边界 | 字节流（无消息边界） | 保留数据报边界 |

**取舍本质**：TCP 用「状态 + 序号 + 重传 + 窗口」换来「可靠有序的字节流」，代价是
延迟、复杂度、队头阻塞；UDP 把这一切交给应用，换来极简与低时延。

- **用 TCP**：要求字节不丢不乱的场景——网页(HTTP/1.1,2)、文件传输、SSH、数据库连接、邮件。
- **用 UDP**：能容忍丢包、更怕延迟，或要自己掌控可靠性的场景——DNS（一问一答）、
  实时音视频/游戏（迟到的包不如丢掉）、QUIC/HTTP3（在 UDP 上自建更灵活的可靠层，
  绕开内核 TCP 的队头阻塞）、各种自定义协议。

经验法则：**先问「丢一个包我能不能忍」。** 忍不了用 TCP；忍得了、且更在乎实时性，
用 UDP 自己加最小可靠层。

## 5. 对照 proper/S11（只做了 UDP）：升级成 TCP 至少要补哪些机制？

`proper/S11` 我们实现的是 UDP-only——能 `sendto/recvfrom` 一包数据报，但没有连接、
不保证到达与顺序。要把它长成 TCP，至少得补：

1. **连接状态机**：每条连接维护一台本课这样的状态机（CLOSED/SYN_SENT/.../TIME_WAIT），
   以及一张「连接表」按四元组 `(本地IP:port, 远端IP:port)` 查找——UDP 是无状态的，
   收到包直接交付；TCP 必须先按四元组定位到那条连接的状态。
2. **三次握手 / 四次挥手**：SYN/FIN 的收发与状态转移（本课主体）。
3. **seq/ack 与可靠重传**：给每个字节编号，维护 `snd_nxt/rcv_nxt`；发送方缓存已发未确认
   的数据 + 重传定时器（RTO，由 RTT 估计），收到对应 ACK 才丢弃，超时则重传。
4. **接收端重组**：按 seq 把乱序到达的段排好、去重，向上层交付**连续**的字节流。
5. **滑动窗口（流量控制）**：通告 window，发送方据此限制在途数据。
6. **拥塞控制**：cwnd + 慢启动/拥塞避免/快重传快恢复（工程上的大头）。
7. **校验与杂项**：校验和、`TIME_WAIT` 端口管理、RST 处理、PSH/URG 等标志。

可以看出：**UDP→TCP 的鸿沟，几乎全在「状态」二字**——UDP 只管单个包，TCP 要为
每条连接持续维护一摞游标和缓冲，并用定时器把不可靠的底层一点点「磨」成可靠有序。
本课只迈出了最关键的第一步：把那台状态机和 seq/ack 推进先走通。
