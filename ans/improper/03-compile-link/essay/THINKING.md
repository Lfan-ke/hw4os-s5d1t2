# 03 · 编译链接 思考题（参考答案）

## 1. ELF 与纯二进制：谁决定每个段落在哪个地址？

链接阶段，是**手写的链接脚本（linker.ld）**决定每个段的 link 地址（VMA）：
`.text` 钉在 `0x80200000`，其后依次摆 `.rodata/.data/.bss`。编译器只产出带名字
的碎片（section），地址布局完全由链接脚本说了算。

加载阶段两者分道扬镳：

- **纯二进制**没有任何自描述元数据，加载器只会把整片字节原样搬到一个固定**加载地址**，
  不做任何重定位。因此它必须满足 **link 地址 == load 地址**：镜像里所有绝对地址
  在链接时就被写死，若把它装到别处，这些绝对引用就全错位。所以裸机 `.bin` 的
  `BASE` 必须等于 `-device loader` 指定的物理加载地址，入口才落在偏移 0。

- **ELF** 自带 **program header**（phdr）表：每个可加载段记录了 `p_offset`（在文件里的位置）、
  `p_vaddr`（VMA，运行时虚拟地址）、`p_paddr`（LMA，物理装载地址）、`p_filesz`、`p_memsz`。
  加载器/动态链接器照着 phdr 把各段从文件搬到指定地址，配合页表把 LMA 映射到 VMA。
  正因为有这张"装载说明书"，ELF 的**加载地址不必等于 link 地址**——LMA 与 VMA 可以不同，
  也可以由 `ld.so` 做重定位后落到任意基址。phdr 帮的忙就是：把"段怎么落地"这件事
  从"写死在字节里"变成"镜像里有元数据可查"。

## 2. .bss 为何不占文件体积（零填充）？

`.bss` 存放初值为 0 的全局/静态数据。既然初值全 0，把这一大片 0 真的写进文件纯属浪费。
所以 ELF 里 `.bss` 段满足 `p_filesz < p_memsz`：文件里只占 `p_filesz`（通常 0）字节，
而运行时要占 `p_memsz` 字节。"**该清多大**"这条信息就编码在 program header 的
`p_memsz - p_filesz`（以及节头表里 `.bss` 的 `sh_size`、链接脚本导出的
`__bss_start/__bss_end` 边界符号）里。

省下的是**镜像文件体积**（零填充不落盘）；甩出去的责任是：加载器/启动代码必须在跳进
`main` 之前，按这条长度信息把 `[__bss_start, __bss_end)` 这段内存**零填充**清零
（裸机就是 `_start` 里那段 `memset` 循环）。纯二进制没有 phdr，这份"清多大"的信息
就得靠链接脚本符号或约定补回来。

## 3. A→B→C 的执行顺序由什么决定？

由 **app 表 / `.apps` 段内的排列顺序**决定，而不是由各 app 自身的代码决定。
runner 只是从 `__apps_start` 到 `__apps_end` 顺序取指针/入口并依次拉起。

**不重新编译任何 app**，只改链接脚本里 `KEEP(*(.apps))` 的输入顺序（或调换 app 表里
指针的次序），就能让 B 先于 A 跑——因为顺序信息在链接产物的那张表里，不在 app 内部。

类比真实串接链 `bootrom → bootloader → kernel`：每一级都只负责"把下一级搬到约定地址再跳过去"，
谁先谁后由上一级手里那张地址表/约定决定，而非被启动者自己。改"先跑谁"等于改那张交接表，
不必重编被启动的镜像。
