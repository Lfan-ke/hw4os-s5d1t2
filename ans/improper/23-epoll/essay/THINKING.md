# 23-epoll 思考题（essay 变体）

在每题下方写下你的理解即可（命中关键字即通过：C10k、就绪式/完成式、水平/边沿、reactor 等）。

## 1. C10k 问题：为什么「一个连接一个线程 + 阻塞 read」扛不住一万个连接？epoll 凭什么能扛？

阻塞 IO 模型里，每个连接配一个线程，线程在 `read()` 上睡着等数据。一万个连接就是一万个
线程：光栈内存（每线程 ~1MB 到 8MB）就吃掉几个 GB，内核调度器在上万个线程间切换，
上下文切换 + 缓存抖动把 CPU 耗光，而其中绝大多数线程其实在干等。这就是 **C10k 问题**：
连接数一上来，「一连接一线程」的资源/调度开销随连接数线性甚至更糟地爆炸。

epoll 的思路是**少量线程 + 事件驱动**：一个（或每核一个）线程用 `epoll_wait` 同时盯着
上万个 fd，只在「某些 fd 真的就绪」时被唤醒，然后只处理这一小撮就绪的 fd。线程数与
连接数解耦（O(核数) 而非 O(连接数)），内存和调度开销都被压下来。

## 2. select/poll 是 O(n)，epoll 是 O(ready)，差别从哪来？

`select`/`poll` 每次调用都要把**全部** fd 的集合从用户态拷进内核、内核**逐个**轮询其
就绪态、再把结果拷回来——一次调用的代价正比于**关注的 fd 总数 n**，哪怕只有 1 个就绪也得
扫一万次（本实验 `select_scan` 的计数器 = n）。

epoll 把「关注集」(`epoll_ctl` 注册的兴趣集) 常驻内核**一次注册、多次复用**，并由内核在
fd「**变就绪那一刻**」(回调) 把它挂上一条**就绪链表**；`epoll_wait` 只遍历这条就绪链表，
代价正比于**当前就绪的 fd 数 ready**（本实验 `epoll_wait` 的 `scan` 计数器 = ready）。
1 个就绪 / 1000 个 fd 时，epoll 检视 1 次、select 检视 1000 次——这就是 O(ready) vs O(n)。

## 3. 水平触发 (LT) vs 边沿触发 (ET)：各自语义？ET 为什么必须把 fd 读到 EAGAIN？

- **水平触发 LT**（默认）：只要 fd **当前**满足条件（如缓冲区里还有数据可读），每次
  `epoll_wait` 都会**持续**报告它。你这次没读完，下次 wait 它还在——稳，不容易丢事件。
- **边沿触发 ET**：只在状态**发生变化的那一刻**（不可读→可读的**上升沿**）报告**一次**。
  之后即使数据还在，只要没有新的「沿」，`epoll_wait` 就**不再**报告。

所以 ET 下你被通知后**必须把这个 fd 一直读到 `EAGAIN`**（读干净为止），因为内核不会再
提醒你「还有剩货」。少读了，剩下的数据要等到**下一次新数据到达**触发新沿才会被发现，
否则就**饿死**了。代价换来的好处：事件更少、`epoll_wait` 返回的列表更短、惊群/重复
唤醒更少。本实验里 `edge_ready(prev,cur)=!prev&&cur` 就是这条「沿」的判定：true→true
不算沿(ET 静默)，false→true 才算沿(ET 通知一次)。

## 4. 就绪式 (readiness, epoll) vs 完成式 (completion, io_uring / IOCP)：两种异步范式有何不同？

- **就绪式**（epoll/kqueue/select）：内核告诉你「fd **可以**读了」，**你自己**再发起
  `read()` 把数据搬上来。通知的是「**就绪**」，真正的 IO 还是你在事件循环里同步做的。
- **完成式**（Linux `io_uring`、Windows IOCP）：你**预先**把「读这个 fd 到这块 buffer」
  整个操作**提交**给内核（提交队列 SQ），内核**替你**把 IO 干完，再往完成队列 (CQ) 投递
  一条「**已完成**」。你拿到结果时数据**已经在 buffer 里**了。

完成式省掉了「被通知就绪 → 再系统调用去读」的来回，能批量提交、共享内存环形队列、
减少系统调用次数，吞吐更高，但编程模型更复杂（要管理提交/完成两个环、生命周期更长的
buffer）。一句话：就绪式问「能动手了吗」，完成式说「我帮你办完了」。

## 5. 事件循环 / reactor 模式是怎么把它们串起来的？对照「一连接一线程的阻塞 IO」。

**reactor** 就是一个死循环：`loop { let ready = epoll_wait(...); for fd in ready { dispatch(fd) } }`。
`epoll_wait` 是它的「心脏」——阻塞在这里等事件，一旦有 fd 就绪就把它分派给对应的回调
（handler），回调里做**非阻塞**的 read/write/处理，处理完回到循环顶端继续等。单线程就能
驱动成千上万个连接，CPU 不浪费在「干等」上。

对照阻塞 IO：阻塞模型把「等」分散到每个线程的 `read()` 里——**调度器**替你做多路复用，
代价是海量线程。reactor 把「等」集中到一个 `epoll_wait`——**程序自己**做多路复用，代价是
所有 handler 必须非阻塞、不能在回调里干长活（否则卡住整个循环，叫「block the event loop」）。
Redis、Nginx、Node.js、Netty 都是 reactor。再往上叠多核就是「多 reactor / 每核一个事件
循环」(如 Nginx 多 worker、Netty 的 EventLoopGroup)。
