# F2 微内核 · 思考题参考答案（essay 变体）

## 1. capability 与 POSIX `fd` 都是「整数句柄」，本质区别在哪？

表面上两者都是「一个整数，指向内核里的某个资源」，但权威模型完全不同。

- **POSIX `fd`：进程私有下标 + 环境权威（ambient authority）。**
  `fd` 只是进程 file table 的数组下标，本身不携带「我能对它做什么」的信息。能不能 `open`
  一个路径、能不能 `kill` 某进程，取决于**进程的身份**（uid/gid、capabilities(7)、SELinux 上下文）——
  即「你是谁」决定「你能干什么」。任何代码只要跑在该进程里，就自动继承这套环境权威，
  这正是混淆代理（confused deputy）漏洞的温床：一段被诱骗的代码用进程的全部权限去访问它本不该碰的资源。

- **capability：不可伪造的对象引用 + 自带 rights 位。**
  cap 把「指向哪个对象」和「能做什么」**绑在一张券上**。seL4 的 cap 是内核 CSpace 里的一个
  128-bit 槽，含 `capType`、对象指针、`capCanSend/Grant/Receive` 等权利位；用户态永远拿不到那个
  内核指针，也无法凭空构造一张 cap——只能由内核**派生（mint/derive）**或经 IPC **传递**而来。
  于是「你能干什么」只取决于「你手里攥着哪些券」，而不是「你是谁」。要授权就显式传一张减权的券
  （Zircon 的 `zx_handle_duplicate` 可以「复制时减权」），要收回就 `revoke`（seL4 靠 mapping database
  递归撤销整棵派生树）。这是 capability 安全的核心：**最小权限 + 无环境权威**，从根上消解 confused deputy。

一句话：`fd` 是「一张写着柜子编号的纸，开柜权限挂在你工牌上」；cap 是「一把刻了'只能开 3 号柜、
只能取不能放'的钥匙，钥匙本身即权限，且配不出副本」。本 demo 里 `Cap{rights,target}` 就是这把钥匙：
`target` 是对象引用、`rights` 是权利位，缺 `RIGHT_SEND` 的券连消息都发不出去（`DenyNoRight`）。

## 2. Tanenbaum–Linus 之争里「微内核太慢」的论据是什么？为什么今天看是旧账？

1992 年 comp.os.minix 上，Andrew Tanenbaum 发帖「LINUX is obsolete」，主张微内核（MINIX 式，
把 fs/驱动放用户态）才是现代且可移植的正道，宏内核是 1970 年代的过时设计；Linus Torvalds 回击
说宏内核在**实践与性能**上更优、可移植性靠干净的代码也能拿到。争论的技术核心就是：

- **微内核的性能论据（反方）**：宏内核里一次 `read()` 是一个函数调用；微内核里它变成
  「应用 → 内核 → VFS 服务 → 磁盘驱动服务 → ……」的**多次 IPC 跨地址空间往返**，每跳都要陷入内核、
  切页表、拷消息、过调度器。早期 Mach 这类「第一代微内核」的 IPC 确实重（几十微秒级），
  benchmark 上明显输给宏内核，「微内核慢」由此坐实。

- **为什么是旧账**：Jochen Liedtke 的 L4（1993，《μKernel Construction》《On µ-Kernel Construction》）
  证明 IPC 慢是**实现问题不是原理问题**。关键是 **IPC fastpath**：同步 IPC 时
  ① **跳过调度器**——发送方直接把 CPU 交给已在等待的接收方，不进就绪队列；
  ② **寄存器传短消息**——≤ 几个 word 直接走 `a0..a3`，根本不碰内存；
  ③ **手工内联 + 统一异常出口**——快路径里没有任何函数调用栈帧与异常处理，任一前提不满足就
  `slowpath()` 退回慢路径。seL4 由此把一次同步 IPC 压到**几百 cycle（< 1μs）**。配合现代硬件
  ASID（切地址空间不刷 TLB），跨进程开销已不再是当年的数量级。今天 Fuchsia/Zircon、seL4 在
  手机、车机、国防设备上商用，「微内核太慢」已是 1990 年代的旧账——剩下的是**工程取舍**
  （多一跳 IPC 换故障隔离与最小 TCB）而非「能不能用」。

## 3. seL4 凭什么能把约 9 千行 C 内核完全形式化证明？「最小 TCB」与可证明性是什么关系？

seL4 是世界上第一个**功能正确性被机器证明**的通用 OS 内核（Klein et al., SOSP 2009）。它做得到，
靠两件事：**内核足够小** + **三层精化（refinement）证明**。

- **三层精化**：① Isabelle/HOL 写的**抽象规约**（「内核应该做什么」，约 5K 行）；
  ② Haskell 写的**可执行规约**（「怎么做」，可在模拟器跑）；③ 实际的 **C 实现**。
  证明的内容是「下层的每一个可观察行为都是上层规约行为的子集」——即 C 代码**不会**做出规约
  没允许的事（无 buffer overflow、无 null deref、无未定义行为，且状态转移符合规约）。2014 年更把
  证明延伸到**二进制层**（编译结果与 C 语义等价），连编译器引入 bug 的可能也堵上。代价极高：
  约 20+ 人年、几十万行 Isabelle 证明脚本，且**每改一行内核都要重证**——这正是 seL4 接口个位数、
  极度克制的原因。

- **最小 TCB 与可证明性的关系**：可信计算基（TCB）= 「为保证安全你不得不信任的全部代码」。
  宏内核里 fs、驱动、网络栈全在内核态，任意一处的 bug 都能破坏全局——TCB 是整个内核（数百万行），
  **大到不可能证明**。微内核把这些赶到用户态后，TCB 缩成只剩 IPC + 调度 + cap + MMU 的**几千行**，
  才进入「形式化证明在工程上可行」的尺度。换句话说：**TCB 越小，需要证明的代码越少，证明才做得动**；
  而把代码从 TCB 里挪出去，靠的就是 capability 隔离——没有相应 cap 的用户态服务即便有 bug 也
  伤不到别人（integrity 性质本身也被证明了）。所以「微内核最小机制 → 最小 TCB → 可形式化验证」
  是一条因果链，seL4 正是这条链的终点示范。真实谱系里：seL4（证明派）、Zircon/zCore（工程派，靠
  fuzzing + Rust 类型系统而非证明）、MINIX 3（教学 + reincarnation server 自愈）各占一格。
