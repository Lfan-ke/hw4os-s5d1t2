# 形态 F1 · 宏内核 / 单内核 —— 思考题参考答案（essay 变体）

## 1. 「单内核」和「宏内核」是不是一回事？宏在哪、和微内核的分界线是什么？

**是同一个东西的两个译名**。英文都是 *monolithic kernel*：mono(单) + lithic(石)，
「一整块石头」——所以「单内核」「宏内核」「巨内核」指的都是它。中文社区里
「宏内核」更常见，「单内核」更直译，二者**完全同义**，不要被两个词唬住以为是两种结构。

它「宏(大、整)」在哪：**所有 OS 服务都编译进同一个二进制、跑在同一个特权地址空间里**。
内存管理、进程调度、文件系统、网络协议栈、设备驱动——全在内核态，彼此之间像调用库函数
一样**直接函数调用**（本课的 `syscall_dispatch` 就是这个：`fs_read → sched_pick →
driver_io` 一串直调，`hops=3`、`ipc_msgs=0`）。

和**微内核**的根本分界线是「**哪些服务在内核态、子系统之间怎么通信**」：

- 宏内核：fs/driver/net 都在**内核态**，子系统间是**直接函数调用**（共享地址空间）。
- 微内核：内核态只留最小集（调度/IPC/地址空间），fs/driver/net 被踢到**用户态服务进程**，
  彼此之间靠 **IPC 消息**通信（各自独立地址空间，见 F2）。

一句话：**宏内核共享一块地址空间用函数调用，微内核切成多块地址空间用消息**。
这条线决定了下面两题的全部权衡。

## 2. 为什么 xv6 / Linux 都选宏内核？直调相对 IPC 省了什么？

因为**性能**，而且是数量级的差距。对比一次「让文件系统读一个块」：

- 宏内核：fs 就是内核里的一个函数，**直接 call 过去**。本课模型里它就是
  `fs_read(inode)` 一次普通函数调用——几个时钟周期，不切地址空间、不动特权级。
- 微内核：fs 是另一个用户态进程，得**发一条 IPC 消息**：陷入内核 → 拷贝消息 →
  切到 fs 进程的地址空间（换页表、刷 TLB）→ fs 处理 → 再发消息回来 → 再切回来。
  一来一回是**两次上下文切换 + 两次跨地址空间拷贝**，比一次函数调用贵几十到几百倍。

本课把这点量化成 `MONO_DISPATCH ipc_msgs=0 hops=3`：一次「系统调用」在宏内核里
只是 **3 次函数调用、0 条消息、0 次上下文切换**。系统调用是热路径，一台机器每秒几百万次，
这点开销乘上去就是整机吞吐的生死。

xv6 选它还有第二个理由：**教学简单**。所有子系统在 `kernel/` 一个目录、共享 `struct proc`、
互相 `grep` 得到，2000 行 C 就能把「进程表→调度器→fork→exec→syscall 表→fs」一口气讲完，
不需要先搭一套 IPC 框架。Linux 选它则是历史 + 性能：1991 年 Torvalds 在著名的
「Tanenbaum-Torvalds 论战」里就坚持宏内核性能优先，事实也证明了在通用场景它跑得更快。

## 3. 「一处崩溃全崩」怎么发生？`off=5` 对应真实的什么 bug？微内核为何能挡住？

**根因是「同一地址空间 = 没有隔离边界」**。本课的 `kmem[8]` 就是这一整块内核地址空间：
逻辑上 `[0..4)` 是驱动缓冲、`[4..8)` 是调度器就绪队列，**但这条边界只存在于注释里**，
硬件层面它就是一根连续数组。`driver_dma_write` 故意**不做边界检查**——因为真实宏内核
里驱动和内核本就共享地址空间，没人在中间立墙。于是：

- 合法写 `off=2`：落在驱动缓冲 `kmem[2]`，相安无事，`detect_corruption=false`。
- 越界写 `off=5`：`DRV_BASE+5 = kmem[5]`，**直接踩进调度器的任务1优先级**，把 30 改成 0。
  调度器毫不知情，下一次 `sched_pick` 就挑了错的任务（决策 **1→2**）。
  `detect_corruption=true` 抓到了这次跨子系统破坏——证明根本没有隔离。

对应真实内核里的：**驱动的缓冲区溢出 / 野指针 / DMA 越界 / use-after-free**。一个网卡或
显卡驱动的越界写，因为和调度器、fs、内存分配器同处一个地址空间，就能把内核别处的数据结构
（运行队列、页表、freelist）写花，轻则行为错乱，重则 panic / oops，**整个系统一起倒**。
这就是「一处崩溃全崩」(one bug, whole kernel down)。

**微内核为什么能挡住**：它把驱动放进**用户态进程**，有自己独立的地址空间和页表，MMU
在硬件层面强制隔离。驱动越界写最多打到自己进程的内存，触发缺页被内核捕获、**只崩这个驱动进程**，
而且能被监控进程重启（这正是 QNX / MINIX3 / seL4 主打的高可靠性）。代价就是第 2 题说的
IPC 税。所以 F1↔F2 是一对镜像权衡：**宏内核拿隔离换性能，微内核拿性能换隔离**。

补充——**Linux 的内核模块（LKM）让这个问题更重还是更轻？** 更重。LKM（如第三方驱动）
被动态加载进内核地址空间，和内核享有同样的特权、同一块内存，**没有任何额外隔离**：一个
有 bug 的闭源显卡驱动照样能 oops 整个内核。这也是为什么后来出现 **eBPF**（在内核里跑
受验证器约束的沙箱字节码）、**用户态驱动**（uio / vfio / DPDK / SPDK）、
**Rust for Linux**（用类型系统消除一类内存 bug）等思路——本质都是想在「宏内核的性能」
和「微内核的隔离」之间，把那道缺失的墙一点点补回来。
