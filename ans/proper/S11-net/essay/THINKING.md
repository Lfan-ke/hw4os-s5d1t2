# S11 思考题（参考答案）

## Q1. Internet Checksum 凭什么能「把校验和也算进去后折叠为 0」就算合法？

Internet Checksum 是 16-bit **一补码（反码）和**。发送方先对除校验和字段外的数据求反码和 `S`，
把校验和字段填成 `~S`。接收方把整段（含校验和字段）再求一次反码和：得到 `S + ~S`。
在一补码算术里 `S + ~S = ~0`（全 1，即 `0xFFFF`），而 `cksum_fold` 最后会 `~`，于是结果是 `0`。
所以「全段折叠为 0」是合法的充要表现——接收方无需把存的校验和取出来反推，直接判 0 即可，
这正是这套校验算法被设计得如此优雅、便于硬件/软件流水累加的原因。

回卷（end-around carry）：把 32 位累加里溢出到高 16 位的进位加回低 16 位，等价于一补码加法。
奇数长度时末字节作高字节补 0，保证字对齐。

## Q2. UDP 校验和为什么要把**伪首部**（IP 的源/目的地址、协议号、长度）也算进去？

UDP 头本身只有端口/长度/校验和，**不含 IP 地址**。若校验只盖 UDP 段，那么一个被错误投递
（IP 头被篡改成别的目的地址）的包，传输层无从察觉。把伪首部 `src_ip|dst_ip|0|proto|udp_len`
也纳入校验，等于让传输层**交叉确认网络层的关键信息**：

- 投递到错误主机 → dst_ip 不符 → 校验失败被丢弃；
- 协议号/长度被篡改 → 同样失败。

这是一种跨分层的端到端校验（end-to-end principle）：传输层不完全信任下层，
用极小代价（12 字节参与累加，不真正上线传输）防住「送错门」。代价是 UDP/TCP 校验和与 IP
地址耦合，所以 NAT 改写地址时必须**同步重算**传输层校验和。

## Q3. 为什么所有多字节字段都要手工 `(hi<<8)|lo` 拼，不能强转指针直接读？

网络字节序固定是**大端**（高字节在低地址），而 RV64 主机是**小端**。
若把 buffer 里某 2 字节强转成 `uint16_t*` 解引用，CPU 会按小端把低地址当低字节——
读出来与线上的大端值字节顺序相反（如 `0x0800` 读成 `0x0008`）。
手工 `(data[i]<<8)|data[i+1]` 显式声明「第一个字节是高位」，与主机字节序无关，
在大端/小端机上都正确，也不受对齐限制（报文里 16/32 位字段经常不在 2/4 字节边界）。
这就是 `htons/ntohs` 一族存在的理由——它们封装的正是这套与主机无关的字节摆放。
