# S10 思考题（参考答案）

## Q1. 用户程序为什么经 `ecall` / libc 求服务，而不直接调用内核里的 `console_putchar`？

本课无分页、用户与内核同地址空间，物理上 U 态「能」跳进 `console_putchar` 的地址。
但我们仍坚持走 `ecall(SYS_WRITE)`，原因和 S08 一致、且对「写应用」这件事尤其重要：

1. **ABI 稳定，应用与内核解耦**：用户程序只认「调用号 + 寄存器约定」（`a7`=号、`a0..a2`=参）。
   内核可以重写 `console_putchar`、换驱动、改内部布局，已编译的用户二进制不用重编。
   这正是 GNU/Linux 把 syscall 号和寄存器约定钉成 ABI 的意义。
2. **特权/安检门**：`console_putchar` 内部还要再 `ecall` 给 SBI（M 态），那是特权操作。
   U 态直接调它，碰到特权指令/CSR 就该陷入。受控的系统调用入口才是合法抬权路径。
3. **可移植**：同一份 `app_sort.c` 只要目标 OS 提供 `SYS_WRITE`，换个内核也能跑——
   libc（这里的 `ulib`）就是这层「应用 ↔ 内核」的可移植垫片。

## Q2. 快排的 partition 决定了什么？枢轴选取与最坏情况。

`partition` 把区间重排成「左段 < 枢轴 ≤ 右段」并返回枢轴落定位置 `p`，于是
`quicksort(lo,p-1)` 与 `quicksort(p+1,hi)` 两个子问题独立、不重叠——这是分治正确性的根。
本课用 Lomuto 划分、固定取 `a[hi]` 作枢轴：实现最简，但遇到**已排序/逆序/大量重复**输入会退化为
O(n²)、递归深度 O(n)（可能爆栈）。工程上用「三数取中 / 随机枢轴 / 小区间转插入排序 / 三路划分应对重复键」
缓解，这也是 libc `qsort` 内省排序（introsort：快排 + 堆排序兜底 + 插入排序收尾）的来历。
本课占位 `return hi` 不划分时，两个子问题不再「各就各位」，整段排不好——这正说明划分是快排的心脏。

## Q3. 无栈协程式的「模板引擎/TUI 渲染」与真实系统的对应物是什么？

- 模板引擎是「**扫描 + 状态切换**」的小解释器：普通字符态 ↔ 占位符态。真实世界从
  Jinja2/Handlebars/Go `text/template` 到 shell 的 `${VAR}` 展开，骨架都是这台状态机，
  只是把变量替换扩成条件/循环/管道/转义。
- TUI 渲染是「**结构化文本 → 控制序列**」：我们把 `# 标题`、`**粗体**` 翻成 ANSI 转义
  （`ESC[1m` 等 SGR 参数）。这正是 `ncurses`、`less`、`git log --color`、各类 Markdown
  终端预览器在做的事——终端就是一台以 `ESC[` 开头的转义序列驱动的状态机（呼应「软件能做的，
  也是一台 FSM」）。把渲染和数据分离（模板/主题）是同一种工程智慧：**逻辑与表现解耦**。
