# 正经·S14 · IPC：管道 / 消息队列 / 共享内存握手

> 承接 S05（协作式 `__switch` 任务）与 S04（异步运行时思想）。本课在「两个协作任务」之上，
> 造出进程间通信（IPC）最常见的三种机制，对应 DESIGN-E S14a 同步 IPC + S14b 异步通信的可达成软件模型。

## 0. 这节课在讲什么

两个执行流要交换数据，无非三条路：

1. **管道（pipe）**：一条**字节流**通道。底层是一个**环形缓冲**（ring buffer）：写端往里塞字节、读端往外取字节，满了写阻塞、空了读阻塞。Unix `pipe(2)` 的本质就是内核里这么一段环形缓冲。
2. **消息队列（message queue）**：传的不是无结构字节流，而是一条条**定长消息**。同样是环形队列，只是每个槽位放一个 `struct Msg` 而非一个字节——`push` 整条入队、`pop` 整条出队，天然保持消息边界。
3. **共享内存 + 完成标志握手（shared memory）**：双方直接看同一块内存，最快但最危险。靠一个 **`ready` 标志位**协调：生产者**写完数据后才置位**，消费者**轮询到置位后才读**——即「A 等 B 置某些位」。这正是 SMP 多核直接映射区核间共享槽、virtio vring、网卡 DMA 描述符环的心智。

本课用 S05 的 `__switch` 搭一个最小协作式两任务运行时：生产者写满就 `ipc_yield()` 让给消费者，消费者读空就让回去。单核轮转，谁阻塞谁让出 CPU。

```
环形缓冲：head=读位置, tail=写位置, count=元素数
  满 = (count == 容量)  → 写返回 0      空 = (count == 0) → 读返回 0
  推进：idx = (idx + 1) % 容量
```

## 1. 你要实现的

`kernel/ipc.c` 的四个核心（其余协作循环 / 握手 / 校验全给定）：

- **`pipe_write_byte` / `pipe_read_byte`**：字节流环形缓冲的写 / 读，满 / 空判定靠 `count`。
- **`mq_push` / `mq_pop`**：定长消息环形队列的入 / 出队（整条 `struct Msg` 逐字节拷贝）。

`switch.S`（`__switch`）、`sched.c`（协作式两任务运行时 + 活锁守卫）、`main.c`（测试驱动）、三套生产者/消费者任务体与共享内存握手均已给定。

## 2. 判据

输出含四段：

- `PIPE_PASS`：32 字节流穿过 8 字节环形缓冲，收到的字节序列与发出的逐字节一致。
- `MSG_PASS`：8 条定长消息穿过容量 4 的环形队列，每条内容与边界都对。
- `SHM_PASS`：共享内存握手——消费者等到 `ready` 置位后读，数据与校验和一致。
- `ALL_PASS`：三项全过。

不得出现 `FAIL` / `panic` / `UNEXPECTED`。

```
cd kernel && make kernel.elf
make run      # OpenSBI banner 后见内核输出；跑完内核 k_shutdown 退出 qemu
```

## 3. 完成标准 (DoD)

- [ ] 环形缓冲满 / 空判定正确，下标回绕用取模，写 / 读各推进一个元素。
- [ ] 消息队列整条入 / 出队，不串位、不丢边界。
- [ ] 生产者写满 / 消费者读空时 `ipc_yield()` 让出，两任务协作把数据搬完且不死锁。
- [ ] 能说清「管道字节流 vs 消息队列定长消息」「共享内存为什么必须先写数据后置 ready」。

## 4. 引申

- 把协作式 `ipc_yield()` 换成 **S02 时钟中断抢占**：生产者/消费者无需主动让出。
- 把单生产者-单消费者扩成**多生产者-多消费者**：环形缓冲需要锁 / 原子 head/tail（接 improper/ipc 的 TAS/MUTEX）。
- 给消息队列加**阻塞语义**（满则睡、有空位唤醒），即真正的 `mq_send/mq_receive`。
- 共享内存换成**无锁环形缓冲**（接 S04 异步运行时、SPSC 队列），用 release/acquire 屏障替代轮询。
