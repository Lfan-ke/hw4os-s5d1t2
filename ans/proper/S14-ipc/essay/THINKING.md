# S14 思考题（参考答案）

## 1. 管道（字节流）与消息队列（定长消息）在语义上最关键的区别是什么？各自适合什么场景？

管道是**无结构字节流**：写端塞进去的字节边界在读端**不被保留**。写 3 次各 10 字节，读端可能一次 `read` 拿到 25 字节、下次拿 5 字节——内核只保证字节顺序，不保证「一次读对应一次写」。所以管道适合 shell 流式管线（`cat | grep`）、日志、串行字节传输这类「连续字节流、自己定界（如换行）」的场景。

消息队列传的是**定长（或带长度头的变长）消息**，`push`/`pop` 以**整条消息为单位**，天然保持消息边界：发 N 条就收 N 条，每条完整。适合「请求-应答」「事件通知」这类**消息语义**的场景——接收方不需要自己从字节流里切分包。代价是每条消息有最大长度限制、且要管理槽位。

实现上两者底层都是环形缓冲，区别只是「元素」是一个字节还是一个 `struct Msg`：管道 `count` 数字节、队列 `count` 数消息；满 / 空判定、下标取模回绕的骨架完全一样。这也是为什么本课用同一套环形缓冲心智实现两者。

## 2. 共享内存握手为什么必须「先写完数据、再置 ready」？把这两步反过来会怎样？`fence` 在这里拦的是什么？

共享内存最快（双方直接读写同一块内存、零拷贝），但没有任何内核中介来保证「数据已就绪」。`ready` 标志位就是这个保证：**消费者只在看到 `ready==1` 之后才读 `data`**。因此生产者的契约是「`ready` 置位的那一刻，`data`/`sum` 必须已经全部写好」。

如果反过来——先 `ready=1` 再填 `data`——消费者可能在 `ready` 刚置位、`data` 还没写完时就冲进去读，读到**半成品 / 旧值**，校验和对不上（甚至更隐蔽地，时对时错）。这就是经典的「发布-订阅」内存序 bug。

`fence`（更精确地说 release 语义的屏障）拦的是**乱序**：编译器和 CPU 都可能把「写 data」和「写 ready」重排，让 `ready=1` 先于数据写入对另一方可见。在单核协作式调度里因为不抢占、又有让出点，乱序的窗口被掩盖；但在真正的 SMP 多核（S13 直接映射区核间共享槽）上，少了这道屏障必出错。所以正确写法是：写满数据 → `fence` → 置 `ready`；读侧对称地：见 `ready` → `fence`(acquire) → 读数据。这正对应真实系统里 virtio vring、DMA 描述符环「填好描述符再敲门铃 / 推进 avail idx」的次序。

## 3. 本课是协作式（谁阻塞谁 `ipc_yield()`）。换成抢占式、或多生产者多消费者，环形缓冲要加什么？

协作式单生产者-单消费者下，环形缓冲**不需要任何锁**：任一时刻只有一个任务在跑（无并发），且让出点可控；`head` 只被消费者改、`tail` 只被生产者改，天然无竞争。这就是 SPSC（single-producer single-consumer）队列免锁的根因。

一旦变成**抢占式**（S02 时钟中断可在任意指令处打断）或**多生产者 / 多消费者**，`count`、`head`、`tail` 会被多方并发读改，出现竞态：两个生产者可能同时看到「不满」都去写同一个 `tail` 槽、`count++` 丢更新。最少要加：对 head/tail/count 的**互斥**（自旋锁 / `amo` 原子操作，接 improper/ipc 的 TAS/MUTEX），或改造成**无锁环形缓冲**——用原子 CAS 推进下标、用 release/acquire 屏障替代轮询，并去掉共享的 `count`（改由 head/tail 之差推算）以缩小竞争面。再进一步加**阻塞语义**（满则睡眠、有空位时唤醒）就成了真正的 `mq_send/mq_receive`，需要配合调度器的等待队列。
