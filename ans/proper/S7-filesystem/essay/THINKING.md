# S7 文件系统 · 思考题（参考解）

## 1. 块设备抽象边界：为什么 FS 只依赖 `bread/bwrite`？

文件系统的全部盘上结构（超级块、inode 区、目录项、数据块）都被表达成「第几号块里的某段字节」，
读写只走 `bread(blk,buf)` / `bwrite(blk,buf)` 两个原语。于是底层是 RAM 数组、virtio-blk MMIO
还是真实 SATA 磁盘，对 FS 完全透明——这正是 rcore easy-fs 的 `BlockDevice` trait、Linux 的
`block_device` 层。把「按块寻址的存储」与「字节排布协议」解耦，换盘只换驱动、不动 FS。
本实验把 `g_disk[NBLOCKS][BSIZE]` 换成 MMIO 读写就能跑在真硬件上。

## 2. 为什么把「名字→inode」和「inode→数据块」分两层，而不是一个大哈希表？

- 目录项（dirent: `name[28] + inum`）做「名字→inode」；inode（`type/size/addrs[]`）做
  「inode→数据块」。两层解耦带来三个好处：
  1. **硬链接**：多个目录项可指向同一个 inum，文件有多个名字而数据只存一份；引用计数在 inode 上。
  2. **改名/移动廉价**：只改目录项，不动数据块映射。
  3. **目录本身就是文件**：目录的数据块装的是 dirent 数组，于是「目录树」用同一套 inode/块机制递归表达。
- 若用一个「全路径→数据」的大哈希表，硬链接、目录子树移动、元数据（权限/大小/时间）都无处安放，
  且重命名要重哈希。分层是「间接一层解千愁」的经典体现。

## 3. RAM 盘断电即失，要「掉电不丢」软硬件各需补什么？

- 本实验是 RAM 模型：`bwrite` 写完 `bread` 立刻读到，是纯内存语义，没有持久化、没有写顺序约束。
- **硬件**需提供真正掉电不丢的介质（闪存/磁盘）与明确的「写完成」语义：`bwrite` 返回 ≠ 数据落盘，
  需要 flush/FUA（Force Unit Access）/写屏障，绕过或刷净设备缓存才算真正持久。
- **软件**需在「多个块的更新不可原子完成」前提下保证崩溃一致性：典型手段是**日志（journaling）/
  WAL**——先把「打算做的整组块写」记进日志并落盘，再写就位；崩溃后重放日志，保证要么全做要么全不做。
  还需**写屏障**约束日志与数据的先后顺序（先日志、后就位、再清日志）。这与本实验「写完立即可读」的
  内存语义本质差别：内存里没有「写一半掉电」这种中间态，磁盘上有，所以才需要日志与顺序控制。
