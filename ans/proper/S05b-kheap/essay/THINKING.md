# S05b 思考题（参考答案）

## Q1. 内核为什么需要动态分配器？静态/栈分配不够吗？

不够。内核要管的对象**数量不定、寿命交错**：进程数随负载变化、文件描述符随 open/close 增减、
网络/磁盘缓冲区按需申请。这些都没法在编译期定大小：

- **静态数组**要么开得过大浪费内存、要么开小了撑爆——而且数量是运行期才知道的。
- **栈分配**寿命绑死在函数作用域，函数返回即失效；可一个 PCB 要活到进程退出，跨无数次函数调用。

所以需要一个「按需申请、用完归还、归还的还能复用」的堆。动态分配器就是把一块内存池
变成可反复 `kalloc/kfree` 的资源——这是从「裸机固定布局」走向「真正操作系统」的分水岭。

## Q2. first-fit / best-fit / buddy / slab 各自取舍？

- **first-fit（本实验）**：扫空闲链表取第一个够大的。实现最简、分配快；缺点是低地址端容易
  被切出小碎块、外部碎片偏多。**next-fit** 是其变体（从上次位置继续扫），更均匀但碎片类似。
- **best-fit**：取「最接近请求大小」的块，剩余最小。直觉省内存，实则常留下大量**极小无用碎块**，
  且每次要扫全表。综合不一定优于 first-fit。
- **buddy**：块大小都是 2 的幂，分裂/合并都按「伙伴」成对进行，分配/释放都 O(log n)、
  合并 O(1)，碎片可控（但有**内部碎片**：向上取整到 2^k）。适合页级分配，rcore 常用。
- **slab/对象缓存**：对**固定大小**的高频对象（PCB、inode、网络包头）预切等大槽位，
  分配/释放 O(1)、几乎零外部碎片、缓存友好；代价是每种对象一套 cache。
  通常 slab 建在 buddy/页分配器之上，各司其职。

一句话：通用变长用 buddy/free-list，固定小对象用 slab；教学先用 first-fit free-list 把原理讲透。

## Q3. 什么是外部碎片？coalesce 如何对抗它？没有合并会怎样？

**外部碎片**：空闲内存总量够，但被切成许多**不相邻的小块**，没有一块连续区域够大，
于是稍大的请求失败。典型成因就是「反复分配/释放不同大小，留下一地小洞」。

**coalesce（合并）**：`kfree` 时若被释放块与**地址相邻**的空闲块挨着，就把它们并成一个更大的块。
本实验维护**按地址升序**的空闲链表，正是为了 O(1) 判断「前驱/后继是否紧邻」并合并。

不合并的后果，本实验的 `COALESCE` 关就在演示：连续释放相邻的两个 64 字节块后，
若不合并，它们是两个各自 64 字节的碎块，谁也装不下一个 100 字节的请求——
明明刚腾出 128 字节连续空间却用不上，只能去高地址另切，碎片越攒越多。合并后它们成为一个
大块，请求落在合并区起点，空间被真正回收复用。

## Q4. 对照 Rust 的 `#[global_allocator]`（S01b）——它和本实验是一回事吗？

是同一件事的两种皮肤。Rust 里 `Box::new` / `Vec::push` 背后都调用全局分配器接口
`GlobalAlloc::{alloc, dealloc}`；`#[global_allocator]` 就是把某个分配器实例**挂**成这个全局接口。
内核态没有 std，于是 rcore ch4 自己实现一个（常是 buddy 或链表分配器）挂上去，
`Box`/`Vec`/`String` 立刻在内核里可用。

本实验的 `kalloc/kfree` 正对应 `alloc/dealloc`：只要把它俩按 `GlobalAlloc`（处理 size+align、
失败返回空指针）包一层，就能让 Rust 内核用上同一块 free-list 堆。C 里是手动 `kalloc/kfree`，
Rust 里是编译器替你在 `Box` 析构时调 `dealloc`——分配器内核是一样的。
