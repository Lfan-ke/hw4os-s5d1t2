# S09 思考题（参考答案）

## Q1. crt0 到底有什么用？为什么不让内核直接 `sret` 到用户的 `main`？

因为 `main` 跑起来时，已经默认了一整套**用户态运行环境**，而这套环境得有人先搭好——这正是 crt0 的活：

1. **退出语义**：C 标准里 `main` 用 `return` 结束，但 CPU 不知道「函数返回」该往哪去。
   crt0 在 `call main` 之后接住返回值，调 `exit(code)` 把退出码报给内核——
   没有 crt0，`main` `ret` 会跳回一个未定义的返回地址（栈上是垃圾），直接跑飞。
2. **环境准备**：真实 crt0 还负责传 `argc/argv/envp`、跑全局对象构造器（`.init_array`）、
   设置 TLS、对齐栈、清 `.bss`（本实验由内核 entry 统一清、参数为空，故 crt0 极简）。
3. **职责分层**：内核只认「入口地址 + 栈顶」这个最小契约，剩下「怎么把控制权优雅地交给/收回 `main`」
   是用户运行时的事。内核不该知道 C 的 `main` 长什么样。

所以内核 `sret` 到的是 **crt0 的 `user_start`**，不是 `main`；`main` 是 crt0 调起来的。

## Q2. `printf` 为什么先格式化到缓冲再一次 `write`，而不是边算边一个字符一个字符 syscall？

- **每次 `ecall` 都要陷入内核**：存 32 个寄存器、切特权级、分发、再 `sret` 回来——
  几十上百条指令的固定开销。一个字符一次 syscall，把这开销乘上字符数，慢得离谱。
- **格式化是纯用户态计算**：`%d`→十进制串、`%x`→十六进制串，全是寄存器里算数，
  不需要内核参与。把它和「输出」解耦：先在用户缓冲里拼好整串，再**一次** `write(1, buf, n)`，
  把 N 次陷入压成 1 次。
- 这也是真实 libc 的「带缓冲的流」（行缓冲/全缓冲）背后的同一动机：**攒批，减少陷入次数**。
  代价是需要一块缓冲（本实验 256 字节静态 `pbuf`）和「何时 flush」的策略。

## Q3. bump（指针碰撞）malloc 简单在哪、它放弃了什么？真 `malloc` 多做了什么？

- **简单**：分配 = 「游标对齐 + 越界检查 + 游标 += n」，三五行、O(1)、无元数据、无碎片处理。
  非常适合「只分配、生命周期一致、整体回收」的场景（如一帧渲染、一次请求的 arena）。
- **放弃的是 `free`**：bump 没法单独归还中间某块——游标只进不退，内存只增不减，堆迟早耗尽。
- **真 `malloc` 多做的**：维护**空闲链表 / 分级 bins**，`free` 时把块挂回、**合并相邻空闲块**抗碎片，
  按请求大小选合适的块（best/first fit）；堆不够时经 `brk`/`mmap` **向内核要新内存**而非用静态数组；
  还要管对齐、最小块大小、线程安全（per-thread arena）等。复杂度换来的是「能反复 alloc/free 不漏不碎」。
