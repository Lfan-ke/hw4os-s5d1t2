# S5d 思考题（参考答案）

## 1. 阻塞与自旋的取舍：临界区长短、单核 vs 多核，各该选谁？为什么？

两者都解决“抢不到资源怎么办”，区别在等待方式：

- **自旋**：原地反复试（`while (locked) {}`），不让出 CPU。**优点**是抢到锁时零延迟（无上下文切换）、实现简单；**代价**是等待期间持续空转烧 CPU。
- **阻塞**：把自己挂到等待队列、置 BLOCKED、`__switch` 让出 CPU，睡着期间**完全不被调度、零 CPU 占用**；持有者释放时唤醒它。代价是两次上下文切换（睡 + 醒）。

取舍取决于**等待时长 vs 切换开销**：

- **临界区极短**（几条指令、等待时间 < 一次上下文切换）：自旋更划算——与其花两次切换去睡再醒，不如原地转几圈就抢到了。
- **临界区较长 / 等待时间不确定**（要等 I/O、等另一个任务跑很久）：阻塞更划算——空转那么久纯属浪费，把 CPU 让给能干活的任务。

再叠加**单核 vs 多核**：

- **单核**上自旋几乎总是错的：持锁者和等锁者共用唯一的 CPU，等锁者自旋时持锁者**根本没机会运行去释放锁**——自旋者把唯一的核占满，反而拖死持锁者（活锁式饥饿）。所以单核内核同步**必须用阻塞**（本课就是单核协作，三种原语全是阻塞式）。
- **多核**上自旋才有意义：持锁者在另一个核上跑、马上会释放，本核自旋几圈就能抢到，省下切换开销——这就是 S15 自旋锁的场景。

工程上常二者合一（**自适应**）：先自旋一小段（赌锁马上释放），超过阈值还没抢到再陷入阻塞。Linux `futex` 正是这个思路——用户态先自旋/快路径 CAS，争用了才 `futex_wait` 进内核睡眠。

本课的 `g_block_events` 判据正是要证明“真的阻塞了”：把阻塞替换成自旋让出（`sync_yield`）数据也能搬对，但被阻塞的任务零 CPU 占用、`g_block_events>0`，自旋则恒为 0——这是二者最直接的可观测区别。

## 2. 条件变量为什么必须配一把锁？为什么等待要写成 `while (!条件) wait()` 而不是 `if`？

**为什么配锁**：条件变量本身不保存状态，它只表达“在某个条件上排队等/被通知”。而“条件”（如缓冲非空 `count>0`）是一段**共享状态**，必须有锁保护对它的读改写，否则会有竞态。典型用法是：

```
mutex_lock(m);
while (!cond) condvar_wait(c, m);   // 持锁判断条件；不满足就等
... 操作受保护的共享状态 ...
mutex_unlock(m);
```

关键在 `wait` 必须**原子地“放锁 + 睡眠”**：如果先 `unlock` 再 `block` 两步可被打断，就有“丢失唤醒”窗口——刚 `unlock`、还没 `block`，另一方改了条件并 `signal`，这次 `signal` 落空（此刻没人在睡），随后我们才 `block`，于是**永远睡下去**。条件变量把放锁与入睡做成一个原子动作（本课单核协作下，`unlock→wq_block` 之间没有切换点，天然原子；真实多核要靠把“入队等待”放在持锁状态下完成、再放锁，或用更底层的原子序）。醒来时 `wait` 再帮你**重新拿回锁**，于是回到调用点时你仍持锁、可安全访问共享状态。

**为什么用 `while` 而不是 `if`**：被 `signal` 唤醒**不等于条件一定成立**，原因有三：

1. **虚假唤醒（spurious wakeup）**：某些实现允许 `wait` 无端返回，必须重检。
2. **抢先（被别人取走）**：你被唤醒置 READY 后到真正运行之间，可能有第三者先跑、把刚就绪的资源又消费掉了（如多个消费者抢同一件产品）——醒来时条件又不成立了。
3. **广播唤醒**：`signal_all/broadcast` 唤醒一群等待者，但资源只够一部分，醒来要各自重检。

用 `if` 只判一次就往下走，会在条件其实不成立时误闯临界区（读空缓冲、越界等）。用 `while` 每次醒来都**重检条件**，不成立就接着睡，才是安全的。同理本课的 `mutex_lock` / `sem_down` 也都用 `while` 重检——唤醒只是“给你一次重检的机会”，不是“保证轮到你”。

## 3. 信号量、互斥锁、条件变量三者语义有何区别？分别在什么时候用？

- **互斥锁（Mutex）**：二值、**独占 + 有归属**。同一时刻最多一个持有者，且通常要求“谁加锁谁解锁”。语义就是“进临界区”。用于保护一段共享数据的读改写。本课用 `locked` 标志 + 等待队列实现。
- **信号量（Semaphore）**：**计数**资源，`down`(P) 取一个、`up`(V) 还一个，`count` 可大于 1，**无归属**（`up` 可由任何任务调用，常用于“一方等另一方”的事件/资源计数）。计数 1 的信号量能当锁用，但语义更宽：本课用 `empty`(初值=容量) / `full`(初值=0) 两个信号量精确地为有界缓冲“数空槽 / 数产品”，生产者 `down(empty)…up(full)`、消费者 `down(full)…up(empty)`，天然实现“满则生产者睡、空则消费者睡”。
- **条件变量（Condvar）**：本身**不计数、不保存状态**，只提供“在某条件上等待 / 通知”。必须配一把锁保护那个“条件”。语义是“等待某个由别人维护的谓词成立”。它比信号量更通用——任意复杂条件（不只是计数）都能用 `while(!谓词) wait()` 表达，且条件的全部状态都在你自己的共享变量里、由锁保护。

一句话选型：**保护数据** → 互斥锁；**对资源/事件计数、或一方放行另一方** → 信号量；**等待一个任意复杂的条件谓词成立** → 条件变量（配锁）。三者底层在本课都落到同一对“入等待队列 + 阻塞 / 出队 + 唤醒”，区别只在“何时该阻塞、何时该唤醒”的判定。

**引申：优先级反转。** 用阻塞锁时若三个任务优先级 L<M<H：低优先 L 先持锁，高优先 H 来抢锁被阻塞等 L；此时中优先 M 就绪，抢占了 L（M 不碰锁）——于是 H 被一个比它低的 M 间接“反超”，持锁的 L 迟迟跑不完、H 一直等。经典修法是**优先级继承**：H 阻塞在 L 持有的锁上时，临时把 L 的优先级提到 H，让 L 尽快跑完释放锁，M 就压不住它了。把本课等待队列换成优先级队列、再加继承逻辑，就是实时内核互斥锁的雏形。
