# 正经·S19 · 微内核 vs 宏内核：一个服务两种形态 + 可插拔驱动收尾

> 承接 S14（IPC：管道/消息队列/共享内存）与 S6（驱动模型）、S7（简易文件系统）。
> 本课把**同一个服务**用两种内核形态各实现一遍并对比，再加一道**可插拔驱动注册**为驱动系统收尾。
> 对应 DESIGN-E 正经路线图微内核/宏内核取舍 + 驱动系统收口的可达成软件模型。

## 0. 这节课在讲什么

操作系统把“服务”（文件、网络、驱动……）放在哪，有两种根本形态：

- **宏内核（monolithic）**：服务**就在内核态**，和内核同处一个地址空间。客户要用服务，**直接函数调用**即可——一次 `call`、一次 `ret`，开销近零。代价是：任一服务崩了就拖垮整个内核，没有隔离。Linux 走这条路。
- **微内核（microkernel）**：内核只留最小机制（地址空间、调度、**IPC**），文件/驱动等服务被赶出内核、变成**独立的用户态服务进程**。客户要用服务，只能**发消息**：把请求送进去、等应答回来。好处是隔离——某个服务崩了不影响内核和别的服务；代价是每次调用都要一来一回的 **IPC（陷入 + 消息拷贝 + 上下文切换）**开销。seL4 / QNX / Mach 走这条路。

本课用**同一份服务核心**（`service.c` 里的极简内存文件服务 `svc_create` / `svc_read`，承接 S7），跑**同一份工作负载**，分别走两条路径，对比结果与开销：

```
  宏内核：  client ──直接 call──▶ svc_create/svc_read        （hops = 0）
  微内核：  client ──请求通道──▶ [服务任务] ──应答通道──▶ client
                    每条请求：send→recv→（处理）→send→recv = 4 跳   （hops = 4×8 = 32）
```

微内核路径建在 S5 的 `__switch` 协作式两任务运行时之上：**客户任务**与**服务任务**在单核轮转，靠 `ipc_yield()` 主动让出。一条单槽消息通道（一格消息 + `full` 标志）当请求/应答的桥。

最后是**驱动系统收尾**：一张可插拔的驱动注册表，每个驱动用名字注册自己的 `read` 操作，内核按名字查找并派发——新增设备只需注册、分发逻辑不改（开闭原则），这是 S6 驱动模型的收口形态。

## 1. 你要实现的

- **`kernel/micro.c` 的 `ipc_send` / `ipc_recv`**：微内核 IPC 请求/应答的搬运核心。
  - `ipc_send`：通道满（`c->full`）则 `ipc_yield()` 等对端取走 → 整条消息拷入 `c->msg` → 置 `c->full=1` → `g_ipc_hops++` → `ipc_yield()` 让对端来收。
  - `ipc_recv`：通道空（`!c->full`）则 `ipc_yield()` 等对端送来 → 整条消息拷出 `*out` → 清 `c->full=0` → `g_ipc_hops++`。
- **`kernel/driver.c` 的 `driver_register`**：找第一个空槽（`used==0`），登记名字（`s_cpy`）与函数指针，置 `used=1`，返回槽号；表满返回 `-1`。

`macro.c`（宏内核直接调用 + 基准结果）、`service.c`（服务核心 + 工作负载发生器）、`driver_find` / 收尾测试、`switch.S` / `sched.c`（协作式运行时 + 活锁守卫）、`main.c`（测试驱动）均已给定。

## 2. 判据

输出含四段：

- `MACRO_PASS`：宏内核路径——客户直接调用服务，8 条请求（4 建文件 + 4 回读）结果正确，作为基准。
- `MICRO_PASS`：微内核路径——客户经 IPC 请求/应答间接调用同一服务，结果与宏内核**逐项一致**，且确实付出了 IPC 开销（`ipc hops > 0`）。
- `DRIVER_SYS_PASS`：注册 uart/rtc/blk 三个驱动，按名字派发并核对，未注册名查不到。
- `ALL_PASS`：三项全过。

中间还会打印一行 `[compare] ... hops=0 ... hops=32 ...`，直观对比宏内核（零中介）与微内核（IPC 开销）。

不得出现 `FAIL` / `panic` / `UNEXPECTED`。

## 3. 自测

```sh
cd kernel && make kernel.elf
timeout 20 qemu-system-riscv64 -machine virt -smp 4 -nographic -bios default -kernel kernel.elf
make clean
```

## 4. 范围与简化

- **服务/IPC/驱动全是单核软件模型**：不引入真实 U 态地址空间隔离与陷入（那是 S8/S10 的范畴）。微内核的“用户态服务任务”用 S5 协作式任务建模，“IPC”用单槽消息通道 + `ipc_yield()` 建模——抓住的是**形态对比**（直接调用 vs 消息往返）与**开销量化**（hops），而非真实特权级切换的纳秒数。
- **开销度量**用“IPC 跳数”而非真实周期：宏内核 0 跳、微内核每请求 4 跳，定性地说明微内核为隔离付出的代价，与真实系统“宏内核快、微内核需优化 IPC”的结论同向。
- 驱动 `read` 用纯函数建模设备寄存器读，注册表只演示**机制**（按名字注册 + 派发），不接真实 MMIO。
