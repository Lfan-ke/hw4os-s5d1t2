# 04-3 思考题 · 超线程与共享资源（参考答案）

## 1. 硬件物理线程（超线程 / SMT）

**每线程必须各复制一套的（architectural state，执行身份）**：
- 程序计数器 PC、整套通用**寄存器** GPRs（x1..x31）、浮点寄存器；
- 控制状态寄存器 **CSR**（如 RISC-V 的 `sstatus`/`sepc`/`satp`、x86 的标志位与段/控制寄存器）；
- 重命名映射表、部分流水线寄存器（让两个执行身份在流水线里互不串味）。
- 一句话：凡是「区分‘这是谁在执行、执行到哪’」的状态都要复制——本课的 `Context{ gpr[31], sepc, sstatus, sp }` 就是它的最小模型。

**两线程共享的（最贵的执行后端）**：
- 取指/译码前端、ALU/FPU 等**执行单元**、乱序发射与调度逻辑；
- L1/L2/L3 **缓存**、**TLB**、分支预测器、访存队列。

**为什么共享能加速**：单线程经常因为一次 cache miss 的**访存延迟**而 stall，昂贵的执行单元此刻空转。
给同一套后端再挂一个执行身份，当线程 A 因访存阻塞时，让线程 B 顶上去占用 ALU，
把 A 的**访存延迟**藏在 B 的计算背后，抬高整体吞吐（延迟掩盖 / latency hiding）。

**省下的开销**：不必复制整套昂贵的乱序执行后端与缓存，只多花极小的**寄存器**面积与功耗
（复制 architectural state），就凭空多出一个「逻辑核」——近一倍的并发身份，却远不到一倍的硅面积。

## 2. 软件进程 / 线程

同进程的多线程**共享**：**地址空间**（`satp` 指向同一页表）、fd 表、堆、代码/全局数据；
**独占**：各自的栈与寄存器**上下文**（就是本课的 TCB.ctx）。

**为什么「切线程」远比「切进程」便宜**：
- 切进程要换 `satp` 等 CSR，导致 **TLB** 整体失效（flush），换进来的进程要重新填 TLB、暖缓存；切线程同属一个地址空间，省掉这步**上下文切换**中最贵的部分；
- 线程间通信直接读写共享内存，免数据拷贝、免 IPC（管道/消息）的内核往返；
- 只需保存/恢复一组通用寄存器 + 少量 CSR（`sepc`/`sstatus`），不动页表。

**「共享反而成负担」的场景**：
- 多线程同写一份共享数据 → **数据竞争**，必须加锁，锁争用串行化、甚至死锁；
- 两线程各改一个变量却落在同一条**缓存**行 → **伪共享**（false sharing），缓存一致性协议反复来回失效，比不共享还慢。

## 3.（可选）两套「共享」的对照

OS 软件线程共享 fd / 地址空间 / 堆；硬件超线程共享 TLB / cache / 执行单元。
两者遵循同一条省钱原则——**复制最少的执行身份（PC + 寄存器 + 少量 CSR），共享最贵的资源**：
软件里「最贵的」是地址空间与已建立的映射（页表、TLB 暖度），硬件里「最贵的」是乱序后端与缓存。
本课的 TCB 把这条原则做实：`Tcb` 只留 `ctx`（一把寄存器）+ 指向 `Process` 的指针，
进程资源（mem/fd/sem）抽到独立的共享结构，绝不在每个执行身份里重复存一份。
