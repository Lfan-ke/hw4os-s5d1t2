# 17 · 思考题参考解（essay · BSP 与设备树）

> 母题：**BSP 是把"散落的硬编码板级常量"收敛成一层可替换的胶水；
> 设备树是 firmware↔OS 的稳定 ABI——平面图不变，店长（OS）随便换。**

## 1. bootloader + 设备树都不变、只升级 OS，为什么仍能开机？

把**设备树当成 firmware↔OS 之间的稳定 ABI**：bootloader/firmware（OpenSBI、U-Boot、UEFI）在启动时把一块描述"这块板长什么样、设备在哪、时钟多快、中断怎么连"的 DTB 放进约定寄存器（RISC-V 是 `a1`），控制权交给内核。内核**不写死任何地址**，而是现场读这张平面图来探测设备。于是 OS 二进制与"具体板子的硬件布局"之间被一层数据契约隔开：

- 只要 DTB 的格式与字段语义（`compatible`/`reg`/`clock-frequency` 的含义）保持兼容，**换一个新内核**照样能解析出同样的 `uart_base`、`clk_hz`，照样点亮 UART、绑定驱动——这正是本课 `parse_dt_v2` 吃**未改动的 v1 DTB** 仍 `UPGRADE_PASS` 验证的事。
- 兼容性要双向：**新内核读老 DT**（本课场景）靠"缺失属性给默认值、不认识的属性跳过而非报错"；**老内核读新 DT** 靠"新增属性是可选的、老内核视而不见"。两者都建立在"未知字段可安全忽略"这条 ABI 纪律上。

**反过来：若新 OS 想用一个 DT 里压根没描述的新设备，谁动手？**

- **重出 DT / 重刷 bootloader**：由"硬件描述的生产者"补一个节点（`compatible`+`reg`+`interrupts`）。代价是要能改 firmware/DT（嵌入式可重烧；云上/服务器的固件 DT 或 ACPI 表往往锁死、需厂商出新版本），但内核侧零侵入、最干净，符合"设备树是单一事实来源"。
- **OS 自己去探测**：内核绕过 DT 直接按已知物理地址戳寄存器、或挂一个"平台设备"。代价是把硬编码地址又搬回了内核（退化成 xv6 `memlayout.h` 的老路）、丧失跨板可移植性、还可能误探到别的设备。
- 工程现实是混合：能枚举的总线（PCIe/USB）让设备自报家门，不能枚举的片上外设老老实实写进 DT/ACPI，**只有迫不得已**（DT 漏描述且无法更新）才在内核里加 quirk/平台数据兜底。

## 2. 同一个 kernel 二进制凭什么跑遍 board A/B？

因为本课的 `kmain` **只认 `cfg.uart_base`**，对"这是哪块板"一无所知；板间差异全被收敛进**一个 `BoardConfig`**。第 1 步用硬编码 `bsp_probe(board_id)` 的 match 表产出它，第 2 步换成 `parse_dt(blob)` 从设备树读出它——`kmain` 一行不改，喂 `A.dtb`(地址 C)/`B.dtb`(地址 D) 就双双点亮（`DT_A_PASS`/`DT_B_PASS`）。

把"硬编码地址"换成"读 DT"：
- **省了**：N 块板不再要 N 份内核或 N 套 `#ifdef BOARD_A`；加一块板只加一份 DTB，二进制完全复用；驱动与"设备具体在哪"解耦。
- **引入的成本**：① 运行期**解析开销**（启动时多一遍遍历，真实 FDT 还要处理大端、对齐、字符串表）；② 对 **DT 正确性的强依赖**——DT 写错一个 `reg` 地址，内核就驱动到错误的物理地址，且这种错很隐蔽（编译期发现不了，要到运行时设备不响应才暴露）；③ 多了一层"谁来保证 DT 与真实硬件一致"的信任链。

**对照 rcore 里写死的 `UART=0x1000_0000`、`CLINT=0x0200_4000`，要"BSP 化 / DT 化"需要动哪几处：**
1. 把 `config.rs`/`memlayout.h` 里那一堆 `const UART_BASE = …` 从**编译期常量**改成**运行期字段**（一个 `BoardInfo { uart, clint, plic, … }` 结构，由启动早期填好，全局只读）。
2. 在 `board_init()`/`start` 里**新增一个解析步骤**：从 `a1` 取 DTB 指针，用 `fdt`/`device_tree` crate 遍历，按 `compatible` 找到 uart/clint/plic 节点，取 `reg` 填进 `BoardInfo`。
3. 把所有**直接引用常量**的地方（console 驱动、定时器、PLIC 初始化）改成读 `BoardInfo` 字段。
4. （可选）`clock-frequency` 等也从 DT 取，替换写死的分频常量。
本质就是把"散落各处的硬编码"收敛成"一个结构 + 一个解析步骤"——这正是 BSP 层存在的意义。

## 3. 驱动靠 `compatible` 字符串去认硬件——灵活在哪、代价在哪？

相比 01-hw-vlan 里**硬连死的 MMIO 地址**（驱动和某个固定地址焊死、换板即废），`compatible` 字符串匹配把"**这是什么设备**"与"**它在哪个地址**"分开：

- **灵活**：新硬件来了只要 DT 补一张"名片"（`compatible="vlab,uart"`+`reg`），内核在**驱动注册表**里按名字认领（本课 `driver_bind` 的 `strcmp` 循环 → `BIND_*_PASS`）；新驱动来了只要往注册表加一条 `{compatible, probe}`，框架代码一行不改。地址、中断号、时钟都从 DT 现取，驱动逻辑与具体板子彻底解耦——"加一个设备 = DT 加一个节点 + 注册一个驱动"。
- **代价**：① 多一层**字符串约定**，`compatible` 拼错/版本不一致就静默匹配不上，且编译期查不出来；② 运行期要遍历 DT × 驱动表做匹配（比直接跳到固定地址多一点开销）；③ 需要一套"从具体到通用"的裁决规则（`["acme,uart-v2","acme,uart","ns16550a"]` 该优先认哪个），否则会误匹配或匹配不到最优驱动。

**放眼真实世界——"板级信息"存在哪、谁产生、谁消费：**

| 体系 | 板级信息载体 | 谁产生 | 谁消费 |
| :-- | :-- | :-- | :-- |
| x86 PC/服务器 | **ACPI** 表（DSDT/SSDT/MADT…，AML 字节码 + `_HID`/`_CID`） | 主板厂商/BIOS/UEFI 固件烧进去 | 内核 ACPI 解析器 + 驱动按 `_HID` 匹配 |
| ARM / RISC-V 嵌入式 | **Device Tree**（DTS→DTB，`compatible`） | 板厂/U-Boot/firmware 随固件提供 | 内核 OF/FDT 解析 + `of_match_table` |
| PCIe / USB | **设备自带配置空间**（Vendor/Device ID、BAR） | 设备硬件自己（即插即用枚举） | 内核总线枚举器按 `vendor:device` 匹配驱动 |

共性：都是**把"硬件描述"从"内核源码"里抽出来**，存进一份内核之外、由硬件/固件侧维护的数据（表、树、或设备自报），内核只做"读描述 → 按标识匹配驱动"。区别在于**谁是事实来源**：ACPI/DT 靠固件**静态描述**不可枚举的片上设备；PCIe/USB 靠设备在**运行期自报**实现热插拔即插即用。本课的 mini-DT + `compatible` 匹配，就是这一整套思想的最小可跑模型。
