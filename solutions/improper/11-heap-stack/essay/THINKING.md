# 11 堆与栈 · 思考题（参考答案）

## 1. 为什么栈「向下生长」、堆「向上生长」是约定而非物理必然？

SP 只是一个能加减的下标/寄存器，往哪个方向挪完全由软硬件约定决定，而非物理定律。
经典布局把代码与静态数据钉在低地址，堆紧随其后**向上生长**（`brk`/bump 游标递增），
栈放在高地址**向下生长**（`push` 时 SP 递减），두者朝中间逼近——这样两个大小都不确定的区域
共享同一段空闲空间，谁用得多谁就多占，利用率最高。

把方向对调（堆向下、栈向上）在「软件模拟」里完全可行：只要 `alloc` 改成游标递减、`push` 改成 SP 递增，
判边界的比较号反过来即可，**程序行为不变**。真正受影响、不能随便改的是与之耦合的**调用 ABI 与现有工具链**：
RISC-V/x86 的调用约定、`call` 压返回地址、帧指针 `fp` 相对 SP 的偏移、栈展开（unwind）信息、
调试器对栈的解释，全都假定了「栈向下」。所以方向是**约定**——一旦定了，整条工具链都按它来，
个人改不动；但它**不是物理必然**。

「先写后减 / 先减后写」（空栈 vs 满栈约定）同理：改变的只是 SP 初值与边界判断那一两行
（满递减栈空时 `sp==top`，先 `sp-=1` 再写；空递减栈则先写再减），**不改变** LIFO 语义、
也不改变「栈是一根会上下挪的指针」这个本质。

## 2. rust 一行 `#[global_allocator]` vs C 手动注册，编译器替你做了哪件事？

rust 里我只写了一行 `#[global_allocator] static GLOBAL: Bump = Bump::new();`，
之后所有 `Box::new`/`Vec::push` 分配的字节就自动落进我的 `Bump` 区域。
**编译器替我做的，是把语言内置的分配入口（`alloc`/`dealloc` 这些 lang item）静态绑定到我这个 static 上**——
即「注册」：让全语言的高层容器都通过我的 allocator 派发。

C 没有这种语言级钩子，于是我**手动**补上同一件事：框架给了一个全局指针 `static Allocator *g_alloc;`
和 `bump_alloc/bump_free`，我必须显式写 `g_alloc = &my_bump;` 把分配器接上去，
再让 `my_malloc/my_free` 经 `g_alloc` 派发。没有这一行注册，`my_malloc` 看到 `g_alloc==NULL` 就返回空，
高层根本拿不到我的内存。所以「注册」的本质，就是**把『分配』这个全局动作指向某个具体的记账员**；
rust 由编译器替你接线，C 要你亲手接线——两边补的是同一根线。

## 3. 比较器检测碰撞 与 硬件 MMU/MPU guard page 的关系？

单设备对向生长里，我靠**一句比较** `heap_top >= sp` 判断堆栈是否相撞——这就是 guard page 的软件版本。
硬件 MMU/MPU 的 guard page，本质也是「在栈底外放一段不可访问的页，越界访问时硬件比较地址并触发缺页」——
**同样是一个比较器**，只不过比较发生在每次访存的硬件流水线里、由页表/区域寄存器驱动，
代价分摊到零（不需软件每步自查），而我的软件比较器要在每次 `alloc`/`push` 手动算一遍。
栈金丝雀（canary）是另一种思路：不比地址而比一个哨兵值是否被改写，用来事后发现溢出。

为什么两块独立设备就天然互不侵犯？因为它们是**两段不同的地址空间（两个不同的数组/游标）**，
一个的游标无论怎么涨都到不了另一个的地盘——隔离是「结构性」的，根本不需要比较器。
代价是：空间被**静态切死**，A 用满了也借不到 B 的空闲。共享同一地址空间（单设备对向生长）正相反：
利用率高、彼此可借空间，但必须**额外**花一个 guard（比较器/页表）来防止互相踩踏。

这正是「**隔离 vs 共享**」的根本取舍：隔离换来「免检的安全」但浪费空间，共享换来「高利用率」但要付保护机制的成本。
真实 OS 的选择是把它们叠起来——进程之间用页表做硬隔离（不同地址空间），进程内部堆栈共享一个地址空间、
靠 guard page 兜底。这一取舍正好承接下一章「12 地址空间」：用软件 MMU 把「稀疏映射 + 隔离」讲透。
