# 16 · 驱动入门 思考题（参考答案）

## 1. 为什么不把设备地址写死，而要绕一圈 dts → dtc → dtb → 解析 → compatible 匹配？

## 答

把地址写死（xv6 在 `memlayout.h` 里 `#define UART0 0x10000000`、`VIRTIO0 0x10001000`）最省事，但代价是**硬件描述被焊死进内核源码**。每换一块开发板——UART 挪了地址、virtio 换了基址、少了一个网卡多了一个 GPIO——都得回头改源码、重新编译一个专供这块板子的内核。N 块板子就是 N 份分叉的内核。

绕这一圈换来的是**“硬件描述”与“内核代码”解耦**：

- **dts** 是人读的硬件清单：每个设备一张“名片”，写明它是谁（`compatible`）、住哪儿（`reg = <base size>`）、用什么中断。
- **dtc** 把名片夹编译成紧凑的二进制 **dtb**（大端、`magic + BEGIN_NODE/PROP/END` 结构块）。
- bootloader/QEMU 启动时把 dtb 指针放进 `a1` 交给内核；内核**运行时解析** dtb，按名片去**驱动表**里认领驱动。

省下的东西：**同一个内核镜像可以跑遍 N 块板子**——板子变了只换 dtb，内核一字节不改。新增设备只要补一张名片 + 贴一个驱动标注，框架代码不动。这正是 Linux 的做法（`arch/*/boot/dts/*.dts` + `of_*` 接口），也是下一课 BSP 的核心：bootloader 与设备树不变、OS 升级时驱动按 `compatible` 复用，无需为每块板重编。本课我自编 `board.dts`、用 `dtc` 编成 `dtb`、再用手写的大端遍历器解析——把这条“解耦链”最小地走了一遍。

代价是多了一层间接（解析开销、要维护 dts），但相对“N 份分叉内核”的维护地狱，这点开销极划算。

## 2. 驱动表字符匹配的裁决：同名、多候选、最具体优先

## 答

我的实现是**最小核**：线性驱动表 + `compatible` 精确字符串相等，命中即停。真实世界要处理两种歧义：

- **两个驱动声明同一 `compatible`**：谁先被命中谁赢（取决于注册/链接顺序），这是脆弱的——Linux 用 `of_device_id` 的优先级、驱动加载顺序、以及 `driver_override` 来消歧，正常不该出现两个驱动抢同一个最具体的字符串。
- **一个设备列多个候选**，从具体到通用，例如 `compatible = ["acme,blink-v2", "acme,blink", "generic-gpio"]`：含义是“我最好是 v2 专用驱动来管，没有就退而求其次用通用 blink 驱动，再不行用最泛的 gpio 驱动”。匹配必须**按列表顺序从最具体到最通用**逐个去驱动表里找，**第一个命中的就用**。

为什么“最具体优先”：专用驱动了解这颗芯片的怪癖（勘误、额外寄存器、时序），能发挥全部功能；通用驱动只保证基本能用。先试具体、后退通用，既能在有专用驱动时拿到最优支持，又能在没有时优雅降级——**向前/向后兼容**两头都照顾到。

会误匹配的例子：若我图省事只按“子串包含”或“前缀”匹配，设备名片写 `"acme,blink"`，而表里有个驱动注册成 `"acme,blink-extreme"`，前缀/子串匹配就可能把它俩错配；又或者两家厂商都用了 `"blink"` 这个太泛的字符串，A 厂的灯被 B 厂的驱动认领，行为全错。所以匹配**必须是整串精确相等**（我代码里就是 `strcmp(a,b)==0` / `a == b`），并且**多候选时严格按从具体到通用的顺序**裁决，绝不能模糊匹配。

## 3. driver derive / 链接段注册：“加一个驱动 = 加一个标注”

## 答

这种“插件自发现”模式我在很多地方见过，本质都是**让插件在编译/链接期把自己登记到一个集合，框架启动时遍历该集合，框架代码对“有哪些插件”一无所知也无需修改**：

- **Linux 内核**：`module_platform_driver()` / `__initcall` 把初始化函数塞进 `.initcall*.init` 链接段，内核启动按 level 遍历调用；`MODULE_DEVICE_TABLE` 导出匹配表供 `depmod`/热插拔自动加载。我的 C 实现用 `__attribute__((section("drivers")))` + `__start_drivers`/`__stop_drivers` 收集，就是这套的最小复刻。
- **Rust 生态**：`inventory` / `linkme` 用链接段在 `main` 之前收集分散登记的项；`ctor` 提供构造期回调。我的 Rust 实现因离线不引第三方 crate，退化成“在 `all_drivers()` 数组里加一行 `driver!(...)`”——同样是“加一行登记、框架遍历逻辑不变”。
- **动态加载**：`insmod`/`dlopen` 在运行期把 `.ko`/`.so` 注册进内核/进程；浏览器扩展、Web 框架的插件目录扫描、`pytest` 按命名约定自动发现测试，都是同构思路。

相对“手写一张全局注册表”（一个集中数组，加驱动要去改它）的成本与风险对比：

| 维度 | 链接段自发现 | 手写全局表 |
| :-- | :-- | :-- |
| 加一个驱动 | 只在驱动自己文件里加一行标注，框架零改 | 要回到中心表里加一行，易冲突、易漏 |
| 链接顺序 | 段内顺序依赖链接器，**顺序不可控**（我代码里就遇到段内对齐补位，要靠存指针 + 跳过空洞绕过） | 顺序由数组显式写定，确定可控 |
| 初始化时机 | 依赖 initcall level / 段被收集的时机，**deferred probe** 等问题随之而来 | 显式调用，时机一目了然 |
| 调试可见性 | “它怎么就被注册了？”不易追踪，符号藏在段里 | 一眼能看全注册了谁 |
| 解耦/可插拔 | 强：第三方模块无需碰框架就能接入 | 弱：第三方要改你的中心文件 |

一句话：自发现用“一点链接器魔法 + 放弃显式顺序与可见性”换来了“框架对插件零耦合、加驱动只加一个标注”的可插拔性；当顺序/依赖很重要时（如 deferred probe、初始化等级），就得额外引入 init level、依赖排序等机制把丢掉的“确定性”再补回来。
