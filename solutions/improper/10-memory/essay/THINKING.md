# 10 · 思考题参考解（essay · swap）

> 母题：**内存只是一层会"骗人"的缓存，慢设备才是真身。**
> 同样两块设备，按"想要什么"拼出三种内存系统；swap 把"看起来很大的内存"建立在"慢而持久的真身"之上。

## 1. thrashing：为什么是"断崖"，不是"斜坡"

工作集**略大于**帧数时，多数访问仍命中驻留帧，只有边缘少数页偶尔换入换出，平均代价只是被慢设备访问轻微拉高——性能近似线性退化。

工作集**远大于**帧数时，几乎每次访问的目标页都在上一轮被挤出去了：FIFO/Clock 选中的 victim 恰是马上又要用的页，于是"换出—立刻换入—又换出"循环往复。命中率塌到接近 0，每次内存访问都退化成一次（甚至两次：脏 victim 还要回写）慢设备 I/O。代价不是慢一点，而是慢 10×、100×——这就是 **thrashing（颠簸）**：曲线在"工作集 ≈ 物理内存"附近出现拐点，越界后近乎垂直跌落，故为"断崖"。

把这一现象放回真实 OS：
- Linux 的 `swappiness`（0–100）调的是内核"多积极地把匿名页换出去给 page cache 腾地方"。调高 → 更早动用 swap、容量更宽裕但更易触发颠簸；调低 → 死守物理内存、宁可回收文件缓存。
- 当连 swap 都换不出有效空间、回收速度跟不上分配速度时，内核请出 **OOM killer** 挑一个进程杀掉——承认"这台机器的真身（物理内存 + swap）装不下当前工作集"。
- 视角统一：**驻留帧只是慢设备（swap/文件）的缓存**。命中=缓存命中，缺页=缓存未命中，victim 回写=脏行写回。所谓"内存不够"，本质是"缓存装不下热数据"。

## 2. 持久为什么必须 sync/write-back，且回写有**顺序**要求

写操作先只改驻留帧（置 dirty 位），并不立刻落到慢设备——这正是缓存"骗人"的地方：你以为写进去了，其实只在易失的快设备里。只有 `sync_all()`（对应 `fsync`/`msync`、内核 `kswapd`/回写线程）把脏页刷回慢设备，数据才真正持久。本实验的 `SYNC_PASS` 就是模拟"掉电后只剩慢设备"，校验内容仍在。

**顺序**要求来自"指针/元数据必须在它指向的数据之后才生效"这条铁律：
- 若先写"元数据说第 N 块已是新数据"，再写数据块本身，而恰在两者之间掉电——元数据指向一块**尚未写入**的旧/垃圾内容，文件系统会"理直气壮地"把垃圾当真数据，造成静默损坏。
- 正确顺序是**先回写数据页，再回写指向它的元数据**（ordered write-back）。`ext4` 的 ordered 日志模式、数据库的 WAL（先写日志再改数据）都是同一思想：保证任何掉电时刻看到的状态要么是旧的一致态、要么是新的一致态，不存在"元数据指向半截数据"的中间态。
- 若 `sync_all` 之前掉电：所有还没刷回的脏页直接丢失，慢设备里仍是上一次同步点的旧内容。能不能接受，取决于上层的一致性契约（丢最近若干秒 vs 丢到不一致）。这就是为什么数据库在提交点强制 `fsync`，以及为什么 journaling 要规定回写顺序。

## 3. 三场景各自换取了什么、放弃了什么

| 场景 | 快/慢怎么用 | 换取 | 放弃 | 真实系统对应 |
| :-- | :-- | :-- | :-- | :-- |
| 一 · 小内存+大存储 | 工作集在 FAST 上算，结果持久回 SLOW | 计算全程走快设备的**速度** + 结果**持久** | 工作集必须塞得进快设备（容量受限），且要显式搬入搬出 | DRAM 当工作内存、SSD/磁盘当仓库；NUMA 近端算、远端存 |
| 二 · 小内存 + 大设备做 swap | FAST 当帧、SLOW 当 swap，缺页换入换出 | **看起来很大**的地址空间 + 持久 | 一旦工作集越界就 thrashing，代价不可预测 | Linux swap 分区/文件、`kswapd`/`vmscan` 换页 |
| 三 · 两块都当内存 | 线性地址译码，FAST/SLOW 焊成一条平坦大内存 | 一步到位的**大容量**、寻址简单、零换页逻辑 | 没有速度分层（落到慢设备的地址就是慢）、断电即失（当内存用就不保证持久） | 分层内存 / CXL 远端内存 / JBOD / NUMA 交织 |

**为什么不"全用快的"**：快设备小、贵、且（本课模型里）断电即失——容量和成本撑不起全部数据，也给不了持久性。
**为什么不"全用慢的"**：慢设备每次访问代价高 10×，把热数据放上面，整个系统被访存拖垮。
所以现实选择是**分层 + 缓存**：把热数据放快的、冷数据/真身放慢的，用 swap/缓存机制在两者间搬运。

**软件 `translate()` 当"虚拟 MMU 垫片" vs 场景三的硬件地址译码器**：
- 软件 `translate()` 省了硬件 MMU/多级页表的电路成本，能灵活表达缺页、换入换出、脏位、victim 选择这些**控制流密集、状态很多**的逻辑（改算法只改代码）；代价是每次访存都要跑一段软件、慢，且需显式调用——真实高性能系统才把它做进 MMU/TLB 硬件。
- 硬件 `mem_decode` 是**纯组合逻辑一拍出结果**，省了软件开销、极快；但它只能做"地址→片选+偏移"这种固定映射，表达不了换页那套有状态的控制流，灵活性被电路结构钉死（位宽、可寻址范围、映射规则都焊死在门里）。
- 一句话：**同一地址映射，软件 if-else 与硬件译码器同构**；软件费时间换灵活，硬件费灵活换速度。
