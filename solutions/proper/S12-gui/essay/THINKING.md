# S12 思考题 · 简易 GUI 与 html/css 转译（参考作答）

## Q1 framebuffer 为什么是 GUI 的"最底层"？软件 framebuffer 与真 virtio-GPU 的差别在哪？

显示硬件的本质是一个**扫描器**：它周期性地把一块约定好格式（分辨率、像素位深、行距 stride）的内存按行扫出去变成屏幕上的光。所以对软件而言，"画图"就退化成"往这块内存的正确偏移写正确的像素字节"——一切线、矩形、字符、窗口最终都落到 `fb[y*stride + x] = pixel`。这就是为什么 framebuffer 是 GUI 的地基：上面的控件、布局、合成器都只是在算"哪些像素该是什么颜色"。

本实验的软件 framebuffer 只有数组本身，没有"被扫描"这一步，所以我们用校验和代替肉眼。真 virtio-GPU 多出的是一套**把这块内存交给 host 显示**的协议：创建 2D 资源并把内存作为 backing 附上去（`RESOURCE_CREATE_2D` + `ATTACH_BACKING`）、用 `SET_SCANOUT` 把资源绑到某路扫描输出，然后每帧把脏矩形 `TRANSFER_TO_HOST_2D` 再 `RESOURCE_FLUSH`。绘制逻辑（怎么算像素）完全一样，差别只在"画完之后怎么让它显示出来"。

## Q2 把 `<div style="color:..">text</div>` 转译成绘制命令，和浏览器渲染管线相比省了什么？

本实验的转译是"一遍扫描、就地绘制"：遇标签取颜色、逐字符按固定 8px 步距画下去、`div` 之间硬编码换行。它省掉了浏览器渲染管线里几乎所有难点：**没有 DOM 树**（不构造节点层级，只顺序扫描）、**没有样式层叠/继承/选择器匹配**（CSS 只认 `color:` 一个内联属性，不解析选择器、优先级、继承）、**没有盒模型与布局**（不算 margin/padding/border、不做正常流/换行/浮动/flex，位置靠游标硬递增）、**没有重排与合成**（一次画完，不维护脏区、不分层合成）。真实管线是 解析→DOM+CSSOM→样式计算→布局(reflow)→绘制(paint)→合成(composite) 的多阶段流水，每阶段都可独立失效与缓存。丐版只保留了最后的 paint，证明"标记→像素"这条链是通的。

## Q3 为什么用 framebuffer 校验和而不是逐像素断言来判对错？这种判法有什么局限？

校验和（这里 FNV-1a）把整块 2048 字节像素压成一个 32 位值，一次比较就能覆盖"每个像素都对"：任何一个像素画错、画漏、位置偏一格，雪崩效应都会让校验和整体改变，断言简单且对绘制 bug 极敏感——很适合自动评测。代价是它**只给"对/不对"，不给"哪里错"**：值不匹配时你看不出是矩形差一行还是字模错一位，得退回去逐区域打印或缩小测试。另一局限是它**对期望值的固化敏感**：framebuffer 尺寸、字模、文档内容一改，期望校验和就得重算，所以它验证的是"与参考实现逐像素一致"，而非"语义上是不是一个合理的 GUI"——后者需要的是结构化断言（某矩形区域是否全红、某文字是否可识别）。
