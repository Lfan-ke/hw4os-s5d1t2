# 形态 F6 · 混合内核：直调与消息的折中路由

> 形态认知专题 · 收尾/加分 —— host 软件直觉 demo（不是完整内核）。
> 一句话母题：**混合内核（Windows NT / macOS XNU）想「两全其美」——把性能关键
> 服务留在内核态直调（快），把需要隔离的服务推到用户态走消息（隔离）。
> 但折中的代价是「两头不靠」：比纯宏内核慢、比纯微内核不隔离。**

## 0. 这节课在讲什么

[04-02 § 3](../../../../tgln/stage2/material/notes/04-02-os-kernel-paradigms.md) 把五种内核
形态摆在「结构维度（谁在内核）」的同一条轴上：

```
全包 ━━━━━━━━━ 折中 ━━━━━━━━━ 最小 ━━━━━━━━━ 无
宏内核(F1)      混合内核(F6)    微内核(F2)      外核
Linux/xv6       NT/XNU          seL4/QNX        jos
全在内核        部分用户态      仅 IPC+sched    只暴露硬件
```

- **F1 宏内核**：fs/net/driver/sched/mm 全在 ring0，服务间是普通 `fn call`（几纳秒）。最快，但 driver bug = 全 OS 崩。
- **F2 微内核**：服务全在用户态，跨服务都走 IPC（陷入+切地址空间+拷贝+回复，~μs）。最隔离，但慢。
- **F6 混合**：**每个服务独立选放在哪**——热路径留内核（快），危险/可替换代码推用户态（隔离）。

本 demo 不写真内核，而用最朴素的软件模型把这个**本质权衡**量化出来：同一份工作
负载，分别按「全直调（F1）/ 混合（F6）/ 全消息（F2）」三种路由跑，统计开销与隔离度。

## 1. 你要填的 1 个函数

软件在 `sw/rust/src/main.rs` 或 `sw/c/hybrid.c`，只填一个 `route`：

```
route(kind) -> Placement      // 按服务类型选 Kernel(直调) 或 User(消息)
```

7 个服务，分两类：

| 服务 | 类型 | 约定放置 | 理由 |
| :-- | :-- | :-- | :-- |
| sched / timer / mm | `Perf` 性能关键 | 内核态直调 `Kernel` | 热路径，受不了 IPC 开销 |
| fs / net / driver / audio | `Isolate` 需要隔离 | 用户态消息 `User` | 第三方代码多，崩了别连累内核 |

开销模型（抽象「时钟拍」）：内核直调 = `1` 拍；用户态消息往返 = `10` 拍，且每次
产生 `2` 条消息（请求 + 回复）。**服务的计算结果与放在哪无关**——放置只改变「开销」
与「隔离」，这正是混合内核的本质：同一个功能，工程师在「快」与「稳」之间选边站。

## 2. 判据

| 子项 | 判据 | 含义 |
| :-- | :-- | :-- |
| 两类服务都跑通 | `HYBRID_PASS` | 既有内核直调服务又有用户消息服务，且都算出正确结果 |
| 折中可量化 | `TRADEOFF_PASS` | 混合开销严格落在 F1 与 F2 之间 + 隔离度居中 + 用户消息计数 > 内核直调计数 |

两段皆过再打印 `ALL_PASS`。失败打印含 `_MISS` 的诊断行（如 `HYBRID_MISS` 退化成纯宏/纯微、
`TRADEOFF_MISS` 折中不成立），不含 `FAIL`/`panic`/`ERROR`。

`TRADEOFF_PASS` 的三条断言对应混合内核的三重身份：

1. **比纯宏慢**：`mono < hybrid` —— 为隔离付出了 IPC 税。
2. **比纯微快**：`hybrid < micro` —— 牺牲了一部分隔离换性能。
3. **隔离税可见**：`kcalls < umsgs` —— 用户态消息事件多于内核直调，IPC 的开销肉眼可见。

→ 这就是「**两头不靠**」：既没有纯宏的极致性能，也没有纯微的彻底隔离。

```
labctl run forms/F6-hybrid      # 跑 rust/c 两条软件路径
labctl watch                    # 边改边自动判定
labctl hint forms/F6-hybrid     # 卡住看提示
```

## 3. 对应真实系统

- **Windows NT（Executive）**：底层 `Microkernel layer`（调度/中断/IPC，小巧像微内核）+
  中层 `Executive`（I/O / Memory / Process / Object Manager 一堆 manager 仍在 ring0，
  把 NT 拉回「宏」）+ 上层 `subsystem`（Win32 / WSL / POSIX 在用户态）。`win32k.sys`
  在 NT 4.0 被从用户态拉进 ring0 求性能——典型的「热路径回内核」。
- **macOS XNU**：`Mach`（微内核，IPC=mach_msg / 调度 / VM）+ `BSD`（VFS / 网络栈 /
  POSIX syscall，宏内核风）+ `IOKit`（C++ 驱动框架，在 ring0）强行融成一个 binary。
  Mach 的 IPC 仍在，但很多操作走 fast-path 直接跳 BSD 层——违背纯微内核原则。
- **本 demo 的 `route`** = NT 的 Cutler / XNU 的设计者面对的同一个选择：每个服务，
  放内核（快）还是放用户态（稳）？没有标准答案，只有权衡。

## 5. 引申（本最小模型 → 真实混合内核）

本课把开销模型硬编码成"直调=1 拍 / 消息=10 拍"、隔离度只用服务计数近似、`route` 是一次性静态决策、只有 7 个服务。按兴趣可沿这些方向逼近真实 NT/XNU 的工程现实：

1. **用真实测量替换硬编码拍数**：拿 seL4/L4 公布的 IPC fastpath cycle、或在本机用 `rdtsc` 测一次真函数调用 vs 一次用户态往返，把 1/10 拍换成真数字，看混合点到底落在哪。
2. **让 route 变成运行时可迁移策略**：复现 NT 4.0 把 `win32k.sys` 从用户态搬进 ring0 求性能、或反向把驱动推到用户态（Windows UMDF / user-mode driver framework）——把"放哪"从编译期定死改成可根据负载/崩溃历史动态调整。
3. **走查真实混合内核源码**：读 XNU 的 `mach_msg` fastpath 与 BSD 层直跳、NT 的 Object Manager / Executive 分层，逐个服务标注"走直调还是走消息"，把思考题 1 的答案落到代码行。
4. **把"隔离度"做成真指标**：当前用服务计数近似隔离，可升级为"故障域大小 / ring0 代码行数 / 崩溃波及范围"，让 `TRADEOFF_PASS` 的"隔离居中"有可解释的量纲。
5. **自适应路由**：给高风险（第三方、崩溃过的）服务自动降级到用户态，对照真实 OS 如何用"用户态驱动 + 崩溃重启"在不改架构的前提下提升稳健性。
6. **对照现代"新混合"**：看 gVisor（用户态 Sentry 拦截 syscall）、microVM（Firecracker）如何在"性能 ↔ 隔离"轴上给出 2020 年代的新折中点——混合内核的命题没有过时，只是换了战场。
